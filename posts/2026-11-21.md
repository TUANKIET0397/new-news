# Tech Radar 21/11/2026: NestJS 12.6 thêm graceful shutdown cho WebSocket và gRPC, loạt MCP server local dính lỗi DNS rebinding

> NestJS 12.6.0 ra ngày 20/11 với nhiều thay đổi hành vi ở microservices: request đang chờ giờ fail với "Connection closed" thay vì treo mãi, gRPC hủy call quá `gracePeriod`, WebSocket có graceful shutdown opt-in. Cùng lúc GitHub Advisory Database công bố một loạt lỗi DNS rebinding ở các MCP server chạy HTTP trên máy local (Todoist, Jupyter, Obsidian), hai lỗi mức Critical. Ai làm NestJS microservices, ai đang chạy MCP server qua HTTP trên laptop, và ai dùng thư viện `effect` để validate input nên đọc kỹ.

## Điểm nóng hôm nay

### NestJS 12.6.0: graceful shutdown cho WebSocket, gRPC hủy call quá hạn, client microservices không còn treo
Bản 12.6.0 phát hành 20/11. Phần "Notable changes" chia ba nhóm:

- Tính năng mới: `NestFactory.create(AppModule, new FastifyAdapter())` tự suy ra kiểu `NestFastifyApplication`, không cần truyền generic nữa (Express và Node adapter cũng vậy). `WsAdapter` có `gracefulShutdown` (mặc định `false`) và `gracePeriod` (mặc định 10.000 ms). gRPC server có `gracePeriod` cho graceful shutdown.
- Đổi hành vi: gRPC server bật `gracefulShutdown` trước đây chờ call đang chạy không giới hạn, giờ call còn chạy sau `gracePeriod` sẽ bị hủy. Một handler override `@Res({ passthrough: true })` bằng `@Res()` thường không còn kế thừa `passthrough`. Route conflict detection đọc host dạng chuỗi như pattern, nên route trên `:tenant.example.com` có thể bị báo trùng. Testing module áp `logger` và `forceConsole` giống `NestFactory`. Trên `@nestjs/platform-fastify`, request có target không bắt đầu bằng `/` nhận 400.
- Microservices: NATS và MQTT server bị đóng trước khi client kết nối thì `listen()` fail với "Connection closed" thay vì vẫn chạy. Client Kafka, MQTT, Redis, RabbitMQ giờ reject request đang chờ với "Connection closed" ở các tình huống trước đây để request chờ mãi (ví dụ Kafka mất partition khi rebalance, RabbitMQ bị broker hủy direct reply-to consumer). Kafka server khi đóng chờ các reply đang xử lý tối đa `gracePeriod` (10 giây). Gateway từ chối client mới ngay khi app bắt đầu đóng.

Theo mô tả PR #18589, khi bật `gracefulShutdown` cho `WsAdapter`: kết nối mới bị từ chối (server HTTP dùng chung trả `503`), frame mới bị bỏ qua nhưng handler đang chạy và `client.send()` đang chờ vẫn hoàn tất, sau đó từng socket nhận close code `1001 Going Away`. Một timer `gracePeriod` duy nhất giới hạn toàn bộ quá trình.

Vì sao đáng chú ý: phần lớn sự cố "deploy xong mất request" ở NestJS microservices đến từ chỗ đóng kết nối không chờ việc đang dở, hoặc ngược lại chờ mãi khiến container bị SIGKILL. Bản này làm hai hướng đó có giới hạn rõ ràng.

Áp dụng: nếu code của bạn từng dựa vào việc `client.send()` treo rồi tự timeout bằng RxJS `timeout()`, giờ sẽ nhận lỗi "Connection closed" sớm hơn, nên kiểm tra lại chỗ bắt lỗi và retry. Có stream gRPC chạy lâu thì tăng `gracePeriod`, nếu không call sẽ bị cắt sau 10 giây khi deploy. Đặt `gracePeriod` nhỏ hơn `terminationGracePeriodSeconds` của Kubernetes hoặc `stop_grace_period` của Docker Compose.

Nguồn: [NestJS v12.6.0 release](https://github.com/nestjs/nest/releases/tag/v12.6.0), [PR #18589: opt-in graceful shutdown cho ws adapter](https://github.com/nestjs/nest/pull/18589)

### MCP server chạy HTTP trên localhost: ba advisory DNS rebinding trong hai ngày
Ngày 19 và 20/11, GitHub Advisory Database đăng một cụm advisory cùng kiểu lỗi: MCP server mở transport HTTP trên máy local nhưng không kiểm tra header `Host` và `Origin`, nên một trang web bất kỳ bạn mở trong browser có thể gọi tool của server đó.

| Package | Mức | Bị ảnh hưởng | Bản vá |
|---|---|---|---|
| `@doist/todoist-mcp` (npm) | Critical | 10.3.2 trở xuống | 10.3.3 |
| `jupyter-mcp-server` (PyPI) | Critical | 1.0.2 trở xuống | 1.0.3 |
| `obsidian-sync-mcp` (npm) | High | 0.5.6 trở xuống | 0.5.7 |

Chi tiết đáng học: `jupyter-mcp-server` đã kiểm tra `Host` và `Origin` ở endpoint `/mcp` (trả 421 khi header giả), nhưng các route quản lý gắn cùng app như `PUT /api/connect` và `DELETE /api/stop` thì không. Kẻ tấn công trỏ server sang một Jupyter giả và nhận luôn token. Với Todoist, middleware duy nhất chỉ kiểm tra token Todoist của chính server, không xác thực người gọi, nên trang độc hại tạo và xóa task bằng API key của nạn nhân.

Vì sao đáng chú ý: "chỉ bind 127.0.0.1 là an toàn" là một giả định sai, và nó không riêng gì MCP. Dashboard admin chạy local, dev server, Redis không mật khẩu publish ra localhost đều cùng lớp rủi ro. Góc học sâu hôm nay giải thích cơ chế.

Áp dụng: nâng ba package trên nếu đang dùng. Với MCP server nói chung, ưu tiên transport stdio cho dùng local (advisory của Todoist ghi rõ stdio không bị browser chạm tới). Nếu buộc phải chạy HTTP thì bật token xác thực, ví dụ `MCP_AUTH_TOKEN` của obsidian-sync-mcp: browser không tự gắn bearer token nên request giả nhận 401.

Nguồn: [GHSA-833v-v58w-294h (todoist-mcp)](https://github.com/advisories/GHSA-833v-v58w-294h), [GHSA-9x8x-crjq-g64h (jupyter-mcp-server)](https://github.com/advisories/GHSA-9x8x-crjq-g64h), [GHSA-mx6p-3fg7-v6pj (obsidian-sync-mcp)](https://github.com/advisories/GHSA-mx6p-3fg7-v6pj)

### Effect 3.22.1: vá ReDoS trong `Schema.TemplateLiteral`, chặn event loop 15 giây bằng 5.000 ký tự
Advisory GHSA-7589-6fvf-x4pw (High, CVSS v4 8.7) công bố 19/11. `Schema.TemplateLiteral` biến mỗi span `Schema.String` thành một wildcard regex lazy. Template có từ hai span `Schema.String` trở lên tạo ra regex có nhiều wildcard mơ hồ, input không khớp làm engine backtrack với thời gian tăng theo lũy thừa ba của độ dài. Trong thử nghiệm của advisory, chuỗi 5.000 ký tự `:` chặn event loop khoảng 15 giây. Ảnh hưởng mọi chỗ decode input không tin cậy: `Schema.decodeUnknown`, `Schema.decodeUnknownSync`, `Schema.is`, payload của `HttpApi` và `@effect/rpc`.

Vì sao đáng chú ý: một request duy nhất làm treo cả process Node.js, mọi request khác phải chờ. Đây là kiểu DoS rẻ nhất có thể.

Áp dụng: nâng `effect` lên 3.22.1. Bản vá dùng phép quét tuyến tính trái sang phải thay cho regex khi mọi span là `Schema.String`. Bài học chung cho mọi validator (Zod, class-validator, Pydantic): giới hạn độ dài trước khi chạy regex.

Nguồn: [GHSA-7589-6fvf-x4pw](https://github.com/advisories/GHSA-7589-6fvf-x4pw)

### Effect: nâng bản vá và chặn độ dài trước template literal
Nâng package:

```bash
npm install effect@3.22.1
```

Nếu chưa nâng được, advisory đưa ra workaround: đặt một schema string có giới hạn độ dài phía trước template. Lưu ý advisory ghi rõ `.pipe(Schema.maxLength(...))` gắn trên chính template không có tác dụng, vì filter chạy sau regex.

```ts
import { Schema } from "effect"

// ví dụ template có hai span Schema.String, dạng bị ảnh hưởng
const MyTemplateLiteral = Schema.TemplateLiteral(Schema.String, ":", Schema.String)

// workaround theo advisory: kiểm tra độ dài trước, rồi mới tới template
const SafeKey = Schema.compose(
  Schema.String.pipe(Schema.maxLength(256)),
  MyTemplateLiteral
)
```

Tốt hơn nữa là chặn body quá cỡ ngay ở tầng HTTP (body parser, reverse proxy) trước khi tới schema.

## Góc học sâu

### DNS rebinding: vì sao bind 127.0.0.1 chưa đủ
Same-origin policy của browser so origin theo tên miền, không theo IP. DNS rebinding lợi dụng chỗ đó:

1. Bạn mở `evil.example`. DNS trả IP server của kẻ tấn công với TTL rất ngắn, trang tải JavaScript về.
2. Script chờ TTL hết rồi gọi `fetch("http://evil.example:8080/mcp")`. Lần phân giải này DNS trả `127.0.0.1`.
3. Browser coi đây vẫn là cùng origin `evil.example`, nên gửi request tới port 8080 trên máy bạn và cho script đọc response. Header `Host` lúc này là `evil.example:8080`.

Server local chỉ kiểm tra "request có tới từ loopback không" sẽ thấy đúng là loopback, vì browser của bạn chính là bên gửi. Thứ duy nhất lộ ra kẻ tấn công là header `Host` (và `Origin` nếu có) mang tên miền lạ.

Các lớp phòng thủ, theo thứ tự từ rẻ tới chắc:

1. Kiểm tra `Host` theo allowlist: chỉ nhận `localhost`, `127.0.0.1`, `[::1]` và tên bạn cấu hình. Lớp này chặn DNS rebinding.
2. Kiểm tra `Origin`: từ chối origin không nằm trong allowlist. Lớp này chặn trường hợp trang web fetch thẳng `http://127.0.0.1:8080` kèm CORS `*`, như advisory obsidian-sync-mcp mô tả.
3. Áp hai lớp trên cho mọi route, trước khi parse body. Bài học từ jupyter-mcp-server: bảo vệ `/mcp` mà quên `/api/connect` là vẫn thủng.
4. Bắt buộc token cho cả server local. Advisory của Todoist nói thẳng: kiểm tra Host và Origin giảm rủi ro DNS rebinding, nhưng không phải là xác thực người gọi. Một client không phải browser trong cùng mạng vẫn giả được hai header.
5. Không cần mạng thì đừng mở mạng: dùng stdio hoặc Unix socket.

Áp vào stack quen thuộc: dev server, admin panel nội bộ, Laravel Telescope hay Horizon chạy local, Swagger UI có nút "Try it out" gọi API thật, container publish `-p 6379:6379` mà Redis không đặt mật khẩu. Cùng một câu hỏi: nếu một tab browser lạ gửi request tới đây, server có phân biệt được không?

### Chủ đề hôm nay: để agent chạy một mình bằng `claude -p`, năm câu hỏi trước khi bấm chạy
Các bài trước đã nói cách prompt, cách plan, cách review khi bạn ngồi trước terminal. Hôm nay là trường hợp ngược lại: agent chạy trong script, CI hay cron, không ai bấm duyệt. Tài liệu Best practices của Claude Code tóm lại: khi bạn còn ngồi đó, agent thiếu context thì vài tin nhắn sau bạn sửa được; khi nó chạy qua đêm, nó có thể xây cả đêm trên một giả định sai.

Trước khi để một task chạy không người trông, tài liệu đề nghị trả lời năm câu hỏi cho đúng task đó:

1. Nó có biết thế nào là xong không? Một điều kiện goal, một file spec, hoặc một test đang fail mà nó phải làm cho xanh.
2. Nó có tự kiểm tra được không? Test suite, một `Stop` hook, một bước review.
3. Nó được chạm vào đâu? Permission rule, `dontAsk`, sandbox, worktree, đúng một nhánh được push.
4. Cái gì dừng nó lại? `--max-turns`, `--max-budget-usd`, giới hạn chi tiêu.
5. Kết quả đi đâu, ai duyệt? Một PR, comment hay bản tóm tắt, rồi một người duyệt merge, deploy, hay bất cứ thứ gì không quay lại được.

Ở dạng script, `claude -p "prompt"` chạy một lần rồi thoát. Các flag tài liệu khuyên gần như luôn dùng:

- `--bare` bỏ qua hook, skill, plugin, MCP server và các file `CLAUDE.md` ở repo lẫn thư mục home, auth lấy từ `ANTHROPIC_API_KEY` hoặc credential của cloud provider. Lưu ý hook truyền qua `--settings` không chạy dưới `--bare`, nên run nào cần hook thì đừng dùng `--bare`.
- `--append-system-prompt`, `--mcp-config`, `--settings` để đưa vào đúng thứ run đó cần.
- `--allowedTools` duyệt trước tool, `--permission-mode dontAsk` từ chối mọi thứ khác lẽ ra sẽ hỏi.
- `--output-format json` cho một object kết quả để parse, `stream-json` kèm `--verbose` để nhận event theo thời gian thực.

Ví dụ trong tài liệu, migrate từng file sang logger API mới:

```bash
for file in $(cat files.txt); do
  claude --bare -p "Migrate $file to the new logger API and commit. Reply OK or FAIL." \
    --allowedTools "Read,Edit,Bash(git add *),Bash(git commit *)" \
    --permission-mode dontAsk \
    --max-turns 20
done
```

Mỗi run trả lời `OK` hoặc `FAIL`, run chạm giới hạn turn thì thoát với lỗi. Tài liệu khuyên chạy thử ba file trước, xem sai ở đâu, sửa prompt, rồi mới chạy phần còn lại.

Câu hỏi số 2 thường bị bỏ qua nhất. Tài liệu đưa ra cách ép kiểm tra bằng `Stop` hook trong `.claude/settings.json`: hook chạy mỗi khi Claude định kết thúc turn, exit code 2 đẩy Claude quay lại làm tiếp, stderr được gửi về làm lý do.

```json
{
  "hooks": {
    "Stop": [
      {
        "hooks": [
          { "type": "command", "command": "pnpm tsc --noEmit 1>&2 || exit 2" }
        ]
      }
    ]
  }
}
```

Nếu hook chặn tám lần liên tiếp mà không có tool call nào ở giữa, Claude Code bỏ qua lần chặn kế tiếp và kết thúc turn, nên không lo vòng lặp vô hạn.

Một template prompt cho job không người trông, gom đủ năm câu hỏi vào prompt:

```text
Task: <một việc cụ thể, một module hoặc một danh sách file>
Done khi: <lệnh test cụ thể> exit 0 và <điều kiện thứ hai nếu có>.
Chỉ sửa file trong <thư mục>. Không đụng migration, .env, file lock.
Nếu cần thông tin không có trong repo, dừng và ghi câu hỏi vào QUESTIONS.md thay vì đoán.
Kết thúc bằng một dòng: OK hoặc FAIL: <lý do>, kèm lệnh đã chạy và 20 dòng output cuối.
```

Dòng "dừng và ghi câu hỏi thay vì đoán" thay cho người không có mặt để trả lời. Dòng cuối ép agent đưa bằng chứng, đúng như tài liệu nhắc: "All tests pass" đứng một mình nói rất ít, đọc output nhanh hơn tự chạy lại, và với phiên bạn không theo dõi thì đó là bằng chứng duy nhất.

Lưu ý từ tin hôm nay: Claude Code 2.1.330 sửa lỗi `claude -p` exit 0 khi ghi ra ổ đầy, nên nâng trước khi tin exit code trong CI.

### Áp dụng ngay hôm nay
Chọn một việc lặp lại nhàm chán trong repo cá nhân (thêm JSDoc cho ba file service, hoặc đổi `console.log` sang logger). Viết vòng lặp `claude -p` như ví dụ trên cho đúng ba file, có `--allowedTools` chỉ gồm `Read`, `Edit` và lệnh test của bạn, `--permission-mode dontAsk`, `--max-turns 15`, và prompt kết thúc bằng `OK` hoặc `FAIL`. Chạy, đọc diff từng file, ghi lại một chỗ prompt cần sửa. Mười lăm phút là đủ cho ba file.
