# Tech Radar 01/11/2026: Node.js 26 lên LTS và loạt bản vá bảo mật TLS/DNS
> Node.js 26 chính thức vào LTS (codename Lithium) sau đợt security release ngày 21/10 vá 10 CVE, trong đó 4 mức High liên quan DNS, TLS hostname và Brotli. NestJS 12.3 thêm adapter HTTP native và cập nhật multer. Nếu bạn chạy Node.js trên VPS hoặc Docker thì nên rà lại phiên bản ngay.

## Công nghệ mới nhất (tra nhanh)

| Công nghệ | Bản mới nhất đã xác minh | Ghi chú |
|---|---|---|
| Node.js | 26.13.0 (LTS, 28/10), 24.22.2 (LTS), 27.0.0-alpha (29/10) | Bản 26 vào LTS, hỗ trợ đến 4/2029 |
| NestJS | 12.3.0 (28/10), 11.2.8 cho nhánh v11 | Có adapter HTTP native `platform-node` |
| Next.js | 16.5.0-canary.36 (31/10) | Mới chỉ là canary, chưa stable |
| Lightpanda | Bản nightly | Headless browser nhẹ, viết bằng Zig |

**Tóm gọn cho người bận:** việc nên làm ngay là nâng Node.js lên bản đã vá bảo mật (22.23.4, 24.22.1 hoặc 26.12.1 trở lên). Còn lại có thể đọc dần.

## Điểm nóng hôm nay

### Node.js 26.13.0 vào LTS (Lithium)
Ngày 28/10, Node.js 26.x chuyển sang LTS với bản 26.13.0, hỗ trợ đến hết tháng 4/2029. Ngoài metadata như `process.release`, bản này không có thay đổi nào so với 26.12.1. Một điểm dễ dính khi nâng cấp từ Node 24 hoặc 22: binary Linux chính thức link với libatomic từ Node 25, nên tùy distro bạn có thể phải cài thêm libatomic trong image Docker. Cùng ngày, Node 24.22.2 (LTS) cũng ra mắt, và 27.0.0-alpha đã xuất hiện ngày 29/10.

Áp dụng: nếu Dockerfile đang dùng `node:24` hoặc `node:22`, đây là lúc lên kế hoạch thử `node:26` ở môi trường staging, và kiểm tra base image slim có thiếu libatomic không.

Nguồn: [Node.js 26.13.0 (LTS)](https://nodejs.org/en/blog/release/v26.13.0)

### NestJS 12.3.0: adapter HTTP native và multer 2.5.0
NestJS v12.3.0 (28/10) thêm `platform-node`, một platform adapter dùng HTTP server native của Node, bên cạnh Express và Fastify (PR #18063). Release notes không nêu tên package npm hay ví dụ dùng, nên hãy đọc docs NestJS trước khi thử. Bản này cũng nâng `multer` lên 2.5.0 theo hướng security update, và map content type multipart không được hỗ trợ sang HTTP 415 (PR #18264). Trước đó, v12.2.0 (19/10) thêm nhiều giới hạn phòng thủ như `maxPendingDataLength` cho SSE, `maxConcurrentMessages` cho `IoAdapter`/`WsAdapter`, `maxErrorMessagesLength` cho `ValidationPipe`.

Cần review khi lên 12.2: `ValidationPipe` mặc định `validationError.target = false` (response lỗi không còn trả object gốc), và `FileTypeValidator` không còn chấp nhận `font/woff2` cho `font/woff`. Ngoài ra nên update `@nestjs/core` cùng lúc với `@nestjs/platform-express`. Nhánh v11 cũng có v11.2.8 (23/10) với nhiều bản vá.

Áp dụng: API upload file dùng multer nên cập nhật sớm; các service có endpoint SSE/WebSocket nên bật các giới hạn mới để tránh bị đẩy memory.

Nguồn: [NestJS releases](https://github.com/nestjs/nest/releases), [v12.3.0](https://github.com/nestjs/nest/releases/tag/v12.3.0)

### Next.js 16.5 canary: Turbopack và `create-next-app`
Nhánh canary v16.5.0 đang ra liên tục (đến canary.36 ngày 31/10). Một số thay đổi đáng chú ý: `create-next-app` không còn hỏi App Router và luôn dùng App Router (canary.32), sửa lỗi treo/crash với response 204 từ Route Handlers, sửa prerender khi `'use cache'` bắt lỗi, và nhiều tối ưu Turbopack. Đây là canary nên chưa phải bản stable, chỉ nên theo dõi.

Áp dụng: dự án Next.js còn dùng Pages Router thì hạn chế dựa vào scaffolding mới; thử canary ở nhánh riêng nếu bạn gặp bug 204 hoặc `'use cache'`.

Nguồn: [Next.js releases](https://github.com/vercel/next.js/releases)

### Lightpanda: headless browser viết bằng Zig cho agent và crawler
Lightpanda (repo đang trending) là headless browser xây từ đầu, không phải fork Chromium, dùng V8 cho JavaScript và có server CDP. README tuyên bố ít hơn khoảng 16 lần peak memory và nhanh hơn khoảng 9 lần so với headless Chrome trong benchmark 100 trang của họ; đây là số liệu của nhà phát triển, chưa kiểm chứng độc lập. Binary Linux/macOS là bản nightly, Linux cần glibc nên không chạy trên Alpine (musl).

Áp dụng: worker scrape hoặc render trên VPS nhỏ, nơi Chrome headless ăn quá nhiều RAM.

Nguồn: [lightpanda-io/browser](https://github.com/lightpanda-io/browser)

## Cài đặt và dùng thử

### Lightpanda
Lệnh lấy từ README chính thức (Linux x86_64, bản nightly):

```bash
curl -L -o lightpanda https://github.com/lightpanda-io/browser/releases/download/nightly/lightpanda-x86_64-linux && \
chmod a+x ./lightpanda
./lightpanda version
```

Dump một trang ra HTML:

```bash
./lightpanda fetch --obey-robots --dump html --log-format pretty --log-level info https://demo-browser.lightpanda.io/campfire-commerce/
```

Chạy server CDP rồi nối Puppeteer:

```bash
./lightpanda serve --obey-robots --log-format pretty --log-level info --host 127.0.0.1 --port 9222
```

```javascript
const browser = await puppeteer.connect({
  browserWSEndpoint: "ws://127.0.0.1:9222",
});
```

Có thể chạy bằng Docker: `docker run -d --name lightpanda -p 127.0.0.1:9222:9222 lightpanda/browser:latest`. Trên Windows cần WSL2.

## Bảo mật cần để ý

Security release ngày 21/10/2026 của Node.js vá các bản **v22.23.4, v24.22.1, v26.12.1**. Trang thông báo không map từng CVE với từng phiên bản vá; hãy nâng lên bản vá mới nhất của dòng đang dùng. Các lỗi mức High:

| CVE | Ảnh hưởng | Tóm tắt |
|---|---|---|
| CVE-2026-105482 | 26.x, 24.x, 22.x | `dns.resolve*()` và `dns.reverse()` cắt hostname tại byte NUL, allowlist có thể bị vượt qua |
| CVE-2026-105483 | 26.x, 24.x | `tls.checkServerIdentity()` coi IP dạng fullwidth digit là hostname, chứng chỉ `DNS:127.0.0.1` có thể được chấp nhận |
| CVE-2026-106069 | 26.x, 24.x, 22.x | Hostname verification đọc octet bắt đầu bằng 0 theo octal, lệch với resolver của OS |
| CVE-2026-111497 | 26.x, 24.x, 22.x | Ghi ngoài vùng nhớ trong Brotli decoder, hậu quả từ crash tới lộ bộ nhớ hoặc RCE |

Mức Medium và Low gồm keep-alive HTTP Agent nhận response sớm (CVE-2026-105481), IPv4 dạng không chuẩn trong SAN (CVE-2026-106072), cache entropy của `randomUUID()` bị lưu vào startup snapshot/SEA (CVE-2026-106074), cùng các lỗi ở `zlib.ZipFile` và permission model (`--allow-fs-read`, `fs.realpathSync`). Bản vá còn cập nhật c-ares, OpenSSL, SQLite, Undici và xử lý việc chứng chỉ CA trung gian eMudhra bị lộ.

Ưu tiên cao nếu app dùng `dns.resolve*()` để kiểm tra allowlist, gọi TLS tới endpoint theo IP, hoặc giải nén Brotli từ dữ liệu không tin cậy (ví dụ response từ upstream, file upload).

Ngoài ra NestJS 12.3.0 kéo `multer` lên 2.5.0 với nhãn security.

## Góc học sâu

### Validate hostname và IP: parse một lần, so sánh trên dạng chuẩn hóa
Hiểu đơn giản: ba lỗi High ở trên đều xảy ra khi hai đoạn code đọc cùng một chuỗi nhưng hiểu khác nhau, nên đoạn kiểm tra cho qua còn đoạn kết nối lại đi tới chỗ khác. `0127.0.0.1` là `87.0.0.1` với WHATWG URL (octal) nhưng resolver của OS có thể đọc thành `127.0.0.1` (decimal). Chuỗi có byte NUL bị kiểm tra ở tầng này nhưng bị cắt ở tầng khác. Giới chuyên môn gọi lớp lỗi này là *parser differential*.

Cách phòng thủ trong backend:

1. Chuẩn hóa input một lần (parse thành cấu trúc, ví dụ địa chỉ IP dạng số) rồi chỉ dùng dạng đã chuẩn hóa cho cả kiểm tra lẫn kết nối.
2. Allowlist phải so sánh trên giá trị sẽ thực sự được dùng để kết nối, không phải chuỗi gốc người dùng nhập.
3. Từ chối thẳng các dạng mơ hồ (octal, hex, số thập phân đơn, ký tự Unicode lạ) thay vì cố đoán.
4. Với tính năng gọi URL do user cung cấp (webhook, import từ URL), chặn dải nội bộ sau khi resolve, và kết nối thẳng tới IP đã resolve để tránh resolve hai lần.

Đây cũng là lý do patch bảo mật cho runtime quan trọng hơn ta nghĩ: lỗi nằm ở thư viện chuẩn mà mọi framework (NestJS, Express, Fastify) đều dùng bên dưới.
