# Tech Radar 15/11/2026: Node.js 27 alpha gom các dns.lookup trùng nhau, Redis 8.12 RC3 vá lỗi TLS session resumption

> Hôm nay không có bản stable lớn nào trong stack chính, nhưng có hai bản pre-release đáng đọc: Node.js 27.0.0-alpha.0.1.0 thêm `subprocess.timedOut` và gom các `dns.lookup()` giống nhau thành một lần gọi `getaddrinfo`, còn Redis 8.12 RC3 sửa lỗi TLS session có thể resume qua listener khác. Phần còn lại là tool quanh coding agent đang lên trending: LoopForge của Tencent, Plannotator và Caveman. Ai viết service Node.js gọi nhiều API bên ngoài, hoặc đang thử đưa agent vào quy trình của team, nên đọc.

## Điểm nóng hôm nay

### Node.js 27.0.0-alpha.0.1.0: `subprocess.timedOut` và gom `dns.lookup()` trùng nhau
Bản alpha thứ hai của dòng 27 ra ngày 12/11 (bản alpha.0 đã nhắc ngày 06/11). Các thay đổi semver-minor đáng chú ý:

- **child_process**: thêm `subprocess.timedOut` cho `spawn()`, `exec()`, `execFile()`, `fork()`. Với `exec()` và `execFile()` cờ này nằm ở `error.timedOut` trong callback. Theo PR, cờ chỉ thành `true` khi option `timeout` gửi được signal kill, và không đảm bảo process đã thật sự thoát.
- **dns**: các lời gọi `dns.lookup()` đồng thời có cùng khóa (hostname, family, hints, order) chỉ tạo một lần `getaddrinfo` trên libuv threadpool, các caller dùng chung kết quả thô rồi tự xử lý option `all`. `dns.resolve()` (c-ares) không đổi. PR không nói có cách tắt.
- **crypto**: tạo chứng chỉ X.509 kèm hỗ trợ CSR.
- **http**: gom body span theo mỗi lần parser chạy; **sea** tạo compile cache cho module VFS; **worker** preload stream vào startup snapshot.
- npm lên 12.2.2, undici lên 8.12.4.

Vì sao đáng chú ý: `getaddrinfo` là lời gọi blocking chạy trên threadpool mặc định chỉ có 4 thread, chung với `fs` và `crypto`. PR đưa ví dụ khi DNS chậm: 100 lookup song song tới cùng một host trước đây xếp hàng thành nhiều đợt, mất hơn 500 giây; sau thay đổi chỉ còn một lần gọi, khoảng 10 giây. Đây là kiểu sự cố hay gặp khi service gọi một API bên ngoài với concurrency cao, hoặc chạy trên WSL. Còn `timedOut` giải quyết chuyện cũ: trước đây bạn không phân biệt được child process bị kill vì timeout hay vì signal từ chỗ khác, nên log lỗi của job chạy `ffmpeg`, `pg_dump` hay script con thường mơ hồ.

Áp dụng: alpha chưa dùng cho production. Trên 26.x hiện tại, nếu service gọi nhiều host ngoài, cân nhắc tăng `UV_THREADPOOL_SIZE` và dùng HTTP agent có keep-alive để giảm số lần lookup. Khi lên 27, thay đoạn đoán timeout bằng `signal === 'SIGTERM'` bằng cờ `timedOut`.

Nguồn: [Node.js v27.0.0-alpha.0.1.0](https://nodejs.org/en/blog/release/v27.0.0-alpha.0.1.0), [PR #62599: dns coalesce lookup](https://github.com/nodejs/node/pull/62599), [PR #66639: subprocess.timedOut](https://github.com/nodejs/node/pull/66639)

### Redis 8.12 RC3: vá TLS session resumption, thêm `ZMOVE` và CPU time trong `SLOWLOG`
RC3 ra ngày 12/11, vẫn là pre-release, Redis ghi rõ không dùng cho production. Điểm chính:

- **Bảo mật (#16127)**: một TLS session có thể được resume trên listener khác (port client so với cluster bus), hoặc sau khi `tls-auth-clients` hay `tls-expected-peer-name` đã đổi, nên bỏ qua kiểm tra của cấu hình mới. Release note không gắn CVE.
- **Lệnh mới**: `ZMOVE`, `BZMOVE`, `ZMOVEMEMBER` di chuyển member giữa các sorted set một cách atomic, theo đầu/cuối, khoảng score hoặc tên, có `COUNT` và điều kiện `NX`/`XX` ở đích.
- **`SLOWLOG GET`** thêm trường thứ 8 là CPU time của lệnh, kèm config `off-cpu-tracking`, để phân biệt lệnh chậm thật với lệnh bị đói CPU.
- Nhiều fix đáng chú ý cho replication và AOF: lệnh có thể replay hai lần khi load AOF sau lỗi ghi, entry `XADD` có `IDMP` có thể mất khi replay; `ZRANGESTORE` có use-after-free khi nguồn và đích trùng nhau.

Vì sao đáng chú ý: `ZMOVE` thay được pattern quen thuộc `ZPOPMIN` rồi `ZADD` (hoặc Lua script) khi chuyển job giữa hàng đợi "pending" và "processing" làm bằng sorted set. Trường CPU time trong slowlog giúp trả lời câu hỏi hay gặp khi Redis chạy chung VPS với app: chậm do lệnh nặng hay do máy hết CPU.

Áp dụng: chưa nâng production. Nếu bạn tự viết delayed queue bằng sorted set, đánh dấu chỗ dùng Lua để chuyển member và thử `ZMOVE` trên môi trường dev khi 8.12 GA. RC1 và RC2 đã nhắc trong bài 03/11.

Nguồn: [Redis 8.12 RC3](https://github.com/redis/redis/releases/tag/8.12-rc3)

## Góc học sâu

### Request coalescing (singleflight): gom các request giống nhau đang chạy dở
Thay đổi `dns.lookup()` trong Node.js 27 là một ví dụ của pattern singleflight: nếu đã có một request cho khóa K đang chạy, request thứ hai cho K không gọi lại backend mà chờ chung kết quả của request đầu.

Bản chất: cache chỉ giúp khi đã có dữ liệu. Ngay lúc cache miss (key hết hạn, deploy mới, cache vừa restart), 500 request cùng lúc cho cùng một sản phẩm hot sẽ cùng thấy miss và cùng đánh vào database. Đó là cache stampede. Singleflight chặn đúng khoảnh khắc này bằng một map từ khóa sang Promise đang chạy:

```typescript
const inflight = new Map<string, Promise<unknown>>();

export function singleflight<T>(key: string, fn: () => Promise<T>): Promise<T> {
  const running = inflight.get(key);
  if (running) return running as Promise<T>;
  const p = fn().finally(() => inflight.delete(key));
  inflight.set(key, p);
  return p;
}

// dùng: 500 request cùng lúc cho product 42 chỉ tạo 1 query
const product = await singleflight(`product:42`, () => repo.findById(42));
```

Ba điều cần nhớ:

1. **Khóa phải gồm mọi thứ ảnh hưởng tới kết quả.** Node.js dùng (hostname, family, hints, order), không chỉ hostname. Nếu kết quả phụ thuộc tenant hay quyền user mà khóa thiếu trường đó, bạn trả dữ liệu của người này cho người kia, giống bài cache key hôm 12/11.
2. **Lỗi cũng được chia sẻ.** Request đầu fail thì cả nhóm fail cùng lúc. Vì xóa khỏi map trong `finally`, request kế tiếp sẽ thử lại thay vì nhận lỗi cũ mãi.
3. **Map này chỉ trong một process.** Chạy 4 instance sau load balancer thì vẫn có tối đa 4 query. Muốn gom giữa các instance cần lock phân tán (ví dụ `SET key value NX PX 5000` trên Redis) hoặc trả dữ liệu cũ trong lúc một worker làm mới (stale-while-revalidate).

Áp dụng: đặt singleflight ngay trước lớp gọi database hoặc API ngoài cho các endpoint đọc nhiều, kết hợp với cache có TTL. Với Go có sẵn package `golang.org/x/sync/singleflight`; với Node.js đoạn trên là đủ cho trường hợp một process.

## Tối ưu dùng AI

### Chủ đề hôm nay: thiết kế tool cho agent, mô tả tool như viết cho đồng nghiệp mới

Khi bạn viết MCP server nội bộ hay thêm function calling vào backend (agent tra đơn hàng, đọc log, tạo ticket), chất lượng của agent phụ thuộc vào tool nhiều hơn vào system prompt. Docs Claude về define tools nói thẳng: mô tả tool chi tiết là "yếu tố quan trọng nhất" với hiệu năng tool use, nên nhắm ít nhất 3 đến 4 câu cho mỗi tool. Bài "Writing tools for agents" của Anthropic bổ sung các nguyên tắc thiết kế. Gom lại thành checklist:

1. **Đừng bọc nguyên từng endpoint.** Thay `list_users` + `list_events` + `create_event` bằng một `schedule_event`; thay `read_logs` bằng `search_logs` chỉ trả dòng liên quan kèm ngữ cảnh. Tool trả về mọi thứ sẽ đốt context.
2. **Namespace theo service và resource**: `orders_search`, `orders_get`, `tickets_create`. Khi số tool tăng, tên rõ giúp model chọn đúng.
3. **Mô tả nói rõ khi nào dùng và khi nào không**, ý nghĩa từng tham số, giới hạn (tool không trả về gì). Tên tham số không mơ hồ: `user_id` thay vì `user`.
4. **Trả về field có nghĩa, ít field.** Ưu tiên `name`, `status`, `created_at` hơn chuỗi UUID nội bộ. Có thể thêm tham số `response_format` với `concise`/`detailed`: ví dụ Slack trong bài viết, bản concise tốn khoảng một phần ba token (72 so với 206).
5. **Phân trang, lọc, cắt bớt với default hợp lý.** Claude Code mặc định giới hạn tool response ở 25.000 token.
6. **Lỗi phải hướng dẫn được cách sửa**: "status phải là một trong pending, paid, refunded", thay vì trả stack trace.
7. **Input phức tạp thì thêm `input_examples`**, mỗi ví dụ phải hợp lệ với `input_schema`, nếu không API trả lỗi 400. Mỗi ví dụ tốn khoảng 20 đến 50 token nếu đơn giản.
8. **Đo bằng transcript.** Anthropic kể Claude tự thêm "2025" vào query của tool web search; sửa mô tả tool là hết.

Template một tool tra đơn hàng cho backend NestJS hoặc Laravel, theo các nguyên tắc trên:

```json
{
  "name": "orders_search",
  "description": "Tìm đơn hàng của cửa hàng theo email khách, mã đơn hoặc trạng thái. Dùng khi người dùng hỏi về tình trạng, lịch sử hoặc số tiền của đơn cụ thể. Không dùng để thống kê doanh thu (dùng reports_revenue). Kết quả tối đa 20 đơn, mới nhất trước; nếu has_more là true, gọi lại với cursor đã trả về. Không trả về thông tin thanh toán như số thẻ.",
  "input_schema": {
    "type": "object",
    "properties": {
      "customer_email": { "type": "string", "description": "Email chính xác của khách, ví dụ an@example.com" },
      "order_code": { "type": "string", "description": "Mã đơn dạng ORD-123456" },
      "status": { "type": "string", "enum": ["pending", "paid", "shipped", "refunded"] },
      "cursor": { "type": "string", "description": "Giá trị cursor từ lần gọi trước, bỏ trống ở lần đầu" },
      "response_format": { "type": "string", "enum": ["concise", "detailed"], "description": "concise chỉ trả mã đơn, trạng thái, tổng tiền; detailed trả thêm danh sách sản phẩm và địa chỉ giao" }
    }
  },
  "input_examples": [
    { "customer_email": "an@example.com", "status": "paid" },
    { "order_code": "ORD-104233", "response_format": "detailed" }
  ]
}
```

Khi nhờ coding agent viết tool, dùng prompt kiểu này:

```text
Viết MCP tool `orders_search` trong src/mcp/orders.tool.ts, dựa trên OrdersService có sẵn.
Yêu cầu:
- description ít nhất 3 câu: làm gì, khi nào dùng, khi nào KHÔNG dùng, giới hạn kết quả.
- Phân trang bằng cursor, tối đa 20 bản ghi mỗi lần.
- response_format concise | detailed; concise không trả UUID nội bộ.
- Lỗi validate trả message nói rõ giá trị hợp lệ, không trả stack trace.
- Viết test cho: không tìm thấy, có trang tiếp theo, status sai.
Chạy test và dán output trước khi báo xong.
```

Một lưu ý mới trong docs: với Claude Fable 5.2, Mythos 5.2, Opus 5.5, Sonnet 5.5, `tool_choice` kiểu `any` hoặc `tool` trả lỗi 400. Muốn chắc chắn input đúng schema, dùng `auto` cùng strict tool use, hoặc structured outputs nếu cần response có dạng JSON cố định.

Nguồn: [Claude Docs: Define tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools), [Anthropic Engineering: Writing tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)

### Áp dụng ngay hôm nay
Mở định nghĩa một tool hoặc MCP tool bạn đang dùng (của team, hoặc một MCP server bạn đã cài). Đếm số câu trong `description`: nếu dưới 3 câu, viết lại theo khung "làm gì, khi nào dùng, khi nào không, trả về gì, giới hạn". Nếu tool không có phân trang hay giới hạn số bản ghi, ghi lại thành một task.
