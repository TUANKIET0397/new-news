# Tech Radar 25/11/2026: Laravel vá lỗi DoS bằng JSON request cho nhánh 12.x, pnpm 12.23 siết credential và dependency local

> Laravel công bố hai advisory mới ngày 23/11, đáng chú ý nhất là lỗi DoS mức High: một JSON request kích thước bình thường đủ làm cạn PHP worker, nhánh 12.x chỉ được vá từ 12.74.0 (ra ngày 24/11). Cùng lúc pnpm 12.23 và 11.29 ra một loạt fix bảo mật chuỗi cung ứng kèm vài breaking change có thể làm gãy CI, còn Hono 4.13.21 siết kiểm tra chữ ký JWT. Ai chạy Laravel 12, dùng pnpm trong CI, hoặc xác thực JWT bằng Hono nên đọc hết.

## Điểm nóng hôm nay

### Laravel 12.74.0 và hai advisory ngày 23/11: DoS qua JSON body, bypass validation bằng key rỗng
Laravel công bố hai advisory trên repo `laravel/framework` ngày 23/11, cả hai do cùng một người báo:

- **GHSA-8h64-cpq2-9h2g, High, CVSS 7.5**: một JSON request "kích thước bình thường" được dựng đặc biệt khiến app tiêu tốn CPU và bộ nhớ quá mức khi xử lý. Theo advisory, attacker không cần đăng nhập, chỉ cần gửi đồng thời vài request như vậy là chiếm hết PHP worker và app ngừng phục vụ. Bản vá: 13.38.0 cho nhánh 13.x, 12.74.0 cho nhánh 12.x. Advisory không công bố đường code bị ảnh hưởng hay payload.
- **GHSA-cq3g-fj94-c8p3, Moderate, CVSS 5.4**: nếu input có phần tử mảng với key là chuỗi rỗng, ví dụ `{"items": {"": {"name": "..."}}}`, các rule trên `items.*` không bao giờ chạy cho phần tử đó. Nguyên nhân là `ValidationRuleParser` khớp segment bằng `[^\.]*` còn `ValidationData::extractValuesForWildcards()` và `Validator::getExplicitKeys()` dùng `[^\.]+`, nên phần tử key rỗng bị bỏ sót. Đã vá ở 13.43.0 và 12.73.0 (cùng đợt 17/11 mà bài 18/11 nhắc tới, giờ mới có advisory chính thức).

Bản 12.74.0 (24/11) còn có fix escape attribute trong Markdown mail ở chế độ secured, backport giới hạn byte cho key trong `TransformsRequest`, và xóa password hash cũ khi đăng nhập user không dùng mật khẩu. Cùng ngày Laravel cũng tag 13.44.0, 13.44.1, 11.57.2, 10.50.5 và 9.52.24, nhưng trang release của các tag này không ghi danh sách thay đổi, nên đừng giả định các nhánh cũ đã có cùng bản vá.

Áp dụng: app Laravel 12 public ra internet nên lên 12.74.0 trong tuần này, vì lỗi DoS không cần xác thực. Với lỗi validation, kiểm tra các endpoint nhận mảng lồng (giỏ hàng, bulk update) mà phía sau tin tưởng dữ liệu "đã validate" để ghi DB: đó là chỗ phần tử lọt rule gây hại nhất.

Nguồn: [GHSA-8h64-cpq2-9h2g](https://github.com/laravel/framework/security/advisories/GHSA-8h64-cpq2-9h2g), [GHSA-cq3g-fj94-c8p3](https://github.com/laravel/framework/security/advisories/GHSA-cq3g-fj94-c8p3), [Laravel v12.74.0](https://github.com/laravel/framework/releases/tag/v12.74.0)

### pnpm 12.23 và 11.29: không đọc `otp` từ file config, chặn dependency `file:` từ package bên ngoài
Cả hai nhánh ra ngày 22/11 với một nhóm fix bảo mật chuỗi cung ứng:

- `otp` không còn được đọc từ file config. Theo release notes, một repository có thể lợi dụng `otp` để gửi một biến môi trường tới registry của chính nó. Giờ phải truyền `--otp` hoặc đặt `PNPM_CONFIG_OTP`; `pnpm config set otp` sẽ báo lỗi.
- Credential registry chỉ được gửi qua HTTPS hoặc HTTP loopback, kể cả khi tải tarball và khi redirect.
- Package không phải local mà khai báo dependency `file:`, `link:` hoặc `workspace:` dạng path sẽ bị từ chối với `ERR_PNPM_LOCAL_SUBDEP_NOT_ALLOWED`.
- `blockExoticSubdeps` giờ được áp cả với entry trong lockfile, kể cả `pnpm install --frozen-lockfile`.
- `pnpm dlx`, `pnx`, `pnpm create` và các lệnh global (`-g`) bỏ qua `.pnpmfile.cjs`, `.npmrc` và `pnpm-workspace.yaml` ở thư mục hiện tại, nên chạy `pnpm dlx` trong một repo lạ không còn thực thi pnpmfile của repo đó.
- `pnpm config get` từ chối in auth setting được bảo vệ, `pnpm config list` ẩn TLS private key và credential trong proxy.

Breaking change ở 12.23 cần kiểm tra trước khi nâng CI: biến môi trường chưa đặt trong `pnpm-workspace.yaml` hoặc `config.yaml` giờ fail với `ERR_PNPM_CONFIG_UNRESOLVED_ENV_VAR` thay vì thành chuỗi rỗng; platform variants bị gỡ, lockfile cũ có ghi variant sẽ làm `--frozen-lockfile` fail với `ERR_PNPM_BROKEN_LOCKFILE` (chạy `pnpm install` để resolve lại); publish package public mà `dependencies` trỏ tới package private trong workspace sẽ fail.

Áp dụng: pipeline nào đang để token hoặc `otp` trong `.npmrc` hay `pnpm-workspace.yaml` với biến kiểu `${NPM_TOKEN}` nên kiểm tra lại: nếu biến không được inject ở một job nào đó, trước đây build vẫn chạy với chuỗi rỗng, giờ sẽ fail ngay. Đây là thay đổi tốt, nhưng nên biết trước để không mất một buổi sáng debug CI.

Nguồn: [pnpm v12.23.0](https://github.com/pnpm/pnpm/releases/tag/v12.23.0), [pnpm releases](https://github.com/pnpm/pnpm/releases)

### Hono 4.13.21: JWT chỉ chấp nhận chữ ký Base64URL chuẩn, client không cho path param đổi host
Bản ngày 23/11 là bản hardening, có bốn người báo cho phần JWT:

- `hono/jwt` từ chối chữ ký không ở dạng Base64URL canonical, tức có padding `=` hoặc có bit thừa khác 0 ở ký tự cuối.
- `hono/client` không còn để một path param làm thay đổi host của request URL khi base URL là relative.

Vì sao chuyện encoding đáng vá: Base64URL cho phép nhiều chuỗi khác nhau decode ra cùng một dãy byte (thêm padding, hoặc đổi các bit không dùng ở ký tự cuối). Chữ ký vẫn hợp lệ về mặt mật mã, nhưng token "khác chuỗi". Hệ thống nào dùng chuỗi token làm key cho denylist (thu hồi token khi logout), cache hay chống replay sẽ bị qua mặt: token đã bị thu hồi chỉ cần đổi một ký tự cuối là không còn khớp denylist.

Áp dụng: nếu bạn tự làm token revocation, lưu `jti` hoặc hash của payload đã verify, đừng lưu nguyên chuỗi token. Với Hono, nâng lên 4.13.21. Phần client đáng để ý nếu path param lấy từ input người dùng rồi đưa vào `hc` client gọi sang service nội bộ.

Nguồn: [Hono v4.13.21](https://github.com/honojs/hono/releases/tag/v4.13.21)

## Cài đặt và dùng thử

### Nâng Laravel lên bản đã vá
Kiểm tra version đang chạy rồi nâng riêng framework (lệnh Composer chuẩn):

```bash
composer show laravel/framework | grep versions
composer update laravel/framework --with-dependencies
php artisan --version
```

Cần ít nhất 12.74.0 (nhánh 12.x) hoặc 13.43.0 (nhánh 13.x) để có cả hai bản vá. Nếu `composer.json` đang khóa kiểu `"laravel/framework": "12.70.*"`, đổi thành `^12.74` trước khi update.

### pnpm 12.23: nâng và bật trì hoãn bản mới phát hành
`pnpm self-update` lấy từ docs chính thức của pnpm. Nếu project ghim pnpm trong trường `packageManager`, lệnh này cập nhật luôn bản ghim đó; nếu pnpm do Homebrew hoặc Corepack quản lý, lệnh không đụng vào bản global.

```bash
pnpm self-update
pnpm --version
pnpm install   # resolve lại nếu frozen install báo ERR_PNPM_BROKEN_LOCKFILE
```

Trì hoãn cài version mới publish, tính bằng phút (mặc định trong docs là 1440, tức một ngày). Cấu hình trong `pnpm-workspace.yaml`:

```yaml
minimumReleaseAge: 1440
minimumReleaseAgeExclude:
  - '@myorg/*'
```

Từ 12.23 có thể áp cho một lần chạy bằng `--minimum-release-age` trên `install`, `add`, `update`, `dlx`. Hai ví dụ khác có trong release notes:

```bash
pnpm remove "eslint-*" "!eslint-plugin-import"
pnpm add foo bar --allow-build=foo,bar
```

## Góc học sâu

### Giới hạn kích thước body chưa đủ: tấn công độ phức tạp khi parse input
Bài 20/11 nói về `max_body_size` của FastAPI. Advisory của Laravel hôm nay là ví dụ cho giới hạn của cách phòng thủ đó: request chỉ có kích thước "bình thường" nhưng vẫn làm sập app. Đây là lớp lỗi gọi là algorithmic complexity attack: attacker không gửi nhiều dữ liệu, mà gửi dữ liệu khiến thuật toán xử lý chạy vào trường hợp tệ nhất.

Vài dạng kinh điển ở tầng parse và validate:

1. **Lồng sâu**: JSON `[[[[...]]]]` vài chục KB có thể sâu hàng nghìn tầng. Parser hoặc code duyệt đệ quy (validate, normalize, transform) tốn stack và thời gian theo độ sâu.
2. **Bùng nổ wildcard**: rule kiểu `items.*.tags.*` phải mở rộng thành một rule cho mỗi phần tử. Mảng 1.000 phần tử, mỗi phần tử 1.000 tag là một triệu rule cần sinh và chạy, trong khi body vẫn chỉ vài MB. Fix "distinct rule trên mảng lớn" trong 12.74.0 thuộc nhóm này.
3. **Hash collision**: nhiều key được chọn để rơi vào cùng bucket biến thao tác O(1) thành O(n), cả mảng thành O(n^2). PHP từng phải thêm `max_input_vars` vì lỗi này với form data.
4. **Regex backtracking (ReDoS)**: một chuỗi vài nghìn ký tự đủ để regex chạy hàng giây. Bài 21/11 có ví dụ với Effect.

Vì sao hậu quả nặng với PHP-FPM: mỗi request chiếm trọn một worker cho tới khi xong. Pool có 20 worker thì 20 request độc hại chạy song song là đủ làm mọi request khác xếp hàng. Node.js còn tệ hơn theo kiểu khác: một request CPU-bound chặn event loop của cả process.

Phòng thủ theo nhiều lớp, không trông vào một chỗ:

- Giới hạn ở edge: kích thước body (`client_max_body_size` của nginx), rate limit theo IP.
- Giới hạn cấu trúc ở parser: độ sâu tối đa, số phần tử mảng tối đa, số key tối đa. Validate các giới hạn này trước khi chạy rule nặng (ví dụ `array|max:100` đặt trước rule cho `items.*`).
- Giới hạn thời gian: `request_terminate_timeout` cho PHP-FPM, timeout ở reverse proxy, để một request xấu không giữ worker mãi.
- Quan sát: metric thời gian xử lý theo route ở p99 và số worker đang bận. Một route thường chạy 50 ms bỗng có request mất 30 giây là tín hiệu cần nhìn ngay.

## Tối ưu dùng AI

### Chủ đề hôm nay: giữ agent đúng phạm vi, chống over-engineering, hard-code để pass test và đoán code chưa đọc
Ba kiểu lỗi hay gặp nhất khi giao task cho coding agent không phải là code sai cú pháp, mà là làm quá phạm vi: sửa một bug thì refactor luôn cả file, thêm abstraction cho một lần dùng, thêm try/catch cho tình huống không thể xảy ra; hoặc làm cho test xanh bằng cách hard-code; hoặc trả lời về một file mà nó chưa mở. Tài liệu prompting best practices của Claude có sẵn prompt mẫu cho cả ba, và chúng dùng được với các agent khác.

Cách dùng hiệu quả là không dán cả ba vào mọi prompt, mà đưa phần phù hợp vào CLAUDE.md hoặc AGENTS.md của repo, rồi chỉ nhắc lại khi thấy hành vi đó xuất hiện. Docs ghi rõ xu hướng over-engineering rõ nhất ở một số model nhất định (Opus 4.5 và 4.6), nên với model khác, thêm luật khi thấy vấn đề chứ đừng thêm phòng xa.

Prompt chống over-engineering, trích từ docs (giữ nguyên tiếng Anh vì model làm theo tốt):

```text
Avoid over-engineering. Only make changes that are directly requested or clearly
necessary. Keep solutions simple and focused:

- Scope: Don't add features, refactor code, or make "improvements" beyond what was
asked. A bug fix doesn't need surrounding code cleaned up. A simple feature doesn't need
extra configurability.

- Defensive coding: Don't add error handling, fallbacks, or validation for scenarios
that can't happen. Trust internal code and framework guarantees. Only validate at system
boundaries (user input, external APIs).

- Abstractions: Don't create helpers, utilities, or abstractions for one-time
operations. Don't design for hypothetical future requirements.
```

Chú ý dòng "Only validate at system boundaries": nó khớp với cách nghĩ backend đúng. Validate ở controller, DTO, webhook handler; không validate lại ở mọi tầng service. Phần Góc học sâu hôm nay là ví dụ boundary đó quan trọng thế nào.

Prompt chống hard-code để pass test (rút gọn từ docs):

```text
Implement a solution that works correctly for all valid inputs, not just the test
cases. Do not hard-code values or create solutions that only work for specific test
inputs. Tests are there to verify correctness, not to define the solution.
If the task is unreasonable or infeasible, or if any of the tests are incorrect,
please inform me rather than working around them.
```

Câu cuối là phần giá trị nhất: cho agent một lối thoát hợp lệ là "báo test sai" thay vì lách. Không có lối thoát đó, agent bị kẹt giữa yêu cầu "làm test xanh" và một test sai, và hard-code là đường ít kháng cự nhất.

Prompt chống đoán code chưa đọc, docs dùng thẻ XML để tách khối:

```text
<investigate_before_answering>
Never speculate about code you have not opened. If the user references a specific file,
you MUST read the file before answering. Make sure to investigate and read relevant
files BEFORE answering questions about the codebase.
</investigate_before_answering>
```

Checklist khi review diff của agent để phát hiện vượt phạm vi:

1. Số file thay đổi có khớp với task không? Sửa một bug trong một service mà diff chạm 8 file là dấu hiệu cần hỏi.
2. Có helper, interface hay config option mới nào chỉ được dùng đúng một lần không?
3. Có `try/catch` hay fallback nào bọc quanh code nội bộ mà trước đó không cần không?
4. Test mới có kiểm tra hành vi, hay chỉ kiểm tra đúng giá trị mà code trả về cứng?
5. File nháp, script tạm có bị để lại không? Docs có prompt riêng: yêu cầu agent xóa file tạm khi kết thúc task.

Nguồn: [Claude prompting best practices: Overeagerness, Avoid focusing on passing tests and hardcoding, Minimizing hallucinations in agentic coding](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)

### Áp dụng ngay hôm nay
Mở diff của PR gần nhất mà agent viết cho bạn, chạy qua 5 câu trong checklist trên. Với mỗi câu trả lời "có", viết một dòng luật ngắn tương ứng vào CLAUDE.md hoặc AGENTS.md của repo (ví dụ: "Bug fix không refactor code xung quanh. Chỉ validate ở controller và DTO."). Tối đa ba dòng, và chỉ thêm luật cho lỗi bạn đã thực sự thấy.
