# Tech Radar 28/11/2026: NestJS 12.6.3 tạo 404 không kèm stack trace, pnpm 12.24 đọc tarball giống hệt npm

> NestJS 12.6.3 giảm khoảng 28 đến 29% CPU cho mỗi response 404 và đổi cách phát hiện route trùng, ai chạy NestJS production nên đọc kỹ phần thay đổi hành vi. pnpm 12.24 đóng một kẽ hở supply chain khi tarball bị đọc khác nhau giữa pnpm và npm. undici 8.14, Vite 8.4 và httpx 0.29 có các thay đổi nhỏ nhưng ảnh hưởng thẳng tới code đang chạy.

## Điểm nóng hôm nay

### NestJS 12.6.3: 404 rẻ hơn, route trùng được phát hiện theo đúng cách router so khớp
Bản ra ngày 26/11, một ngày sau 12.6.1 và 12.6.2 đã nói ở bản tin trước.

Những điểm nên biết:

- **Hiệu năng**: 404 cho route không khớp được tạo mà không capture stack trace, giảm khoảng 28 đến 29% CPU server cho mỗi 404 (#18730). Với API public hay bị bot quét đường dẫn ngẫu nhiên, đây là CPU tiết kiệm được mà không phải sửa gì.
- **Route conflict detection**: so khớp path giống router. Trên Express, `GET /users` và `GET /Users` giờ bị coi là trùng; Fastify với `caseSensitive: false` cũng vậy (#18721). Nếu dự án lỡ khai báo hai route chỉ khác hoa thường, sau khi nâng sẽ thấy cảnh báo.
- **`@Body('key')`** trả `undefined` khi body là primitive falsy như `""`, `0`, `false` (#18720).
- **`ParseDatePipe`** từ chối ngày vượt quá cuối tháng ở một số định dạng (#18724, #18727).
- **Exclusion không ghi version** giờ áp dụng cho cả route của default version (#18601). Ai dùng versioning cùng `setGlobalPrefix({ exclude })` nên kiểm tra lại.
- **Fastify**: request bị client hủy giữa chừng khi đang gửi body trở thành `HttpException` 400 (#18726); `app.listen(port, host, backlog)` truyền backlog đúng (#18736); `StreamableFile` với status 304 không bị đọc và response không có body (#18723).
- **WebSocket**: các gateway dùng chung một socket.io server xử lý mỗi disconnect đúng một lần (#18745).
- **gRPC**: `GrpcExceptionFilter` log lỗi không phải `RpcException` trước khi trả `UNKNOWN` (#18722).

Áp dụng: nâng lên 12.6.3, chạy e2e test cho các endpoint có versioning và các handler đọc `@Body('key')` với giá trị có thể là `0` hoặc `false`. Nếu log monitoring đang đếm lỗi gRPC, sẽ thấy thêm dòng log từ filter.

Nguồn: [NestJS v12.6.3](https://github.com/nestjs/nest/releases/tag/v12.6.3)

### pnpm 12.24.0: đọc tarball như npm hoặc từ chối, thêm `pnpm audit engines` và `pnpm audit deprecations`
Bản ra ngày 26/11.

- **Tarball parsing khớp với npm**: release notes ghi rằng tarball có header mà npm đọc khác đi, ví dụ PAX header bị lỗi, trước đây có thể khiến pnpm cài ra tập file khác với npm. Giờ pnpm đọc mọi tarball theo cách của npm hoặc từ chối hẳn. Đây là kiểu lỗ hổng parser differential: người review package bằng npm thấy một nội dung, máy cài bằng pnpm nhận nội dung khác.
- **`pnpm audit deprecations`**: liệt kê package đã cài bị registry đánh dấu deprecated, exit code `1` nếu có.
- **`pnpm audit engines`**: liệt kê package không hỗ trợ phiên bản Node.js hoặc platform hiện tại, exit code `1` nếu có.
- **`pnpm approve <pkg>`** không còn tự cấp quyền build script và agent skill cho package không có yêu cầu đang chờ; nó hỏi bạn cấp quyền nào. Trong CI hoặc shell không tương tác, phải cấu hình sẵn hoặc dùng `pnpm approve-builds`.
- Exact version có SemVer build metadata giờ khớp đúng trong `minimumReleaseAgeExclude`, `trustPolicyExclude` và `allowBuilds`.
- Sửa lỗi nhiều lần install song song dùng chung store đôi khi copy ra file rỗng hoặc thiếu.

Áp dụng: `pnpm audit engines` là bước CI rẻ để bắt sớm chuyện nâng Node.js trên VPS hoặc image Docker mà một dependency chưa hỗ trợ. Kết hợp với undici 8.14 (cần Node.js 22.19.0+) bên dưới là ví dụ điển hình.

Nguồn: [pnpm v12.24.0](https://github.com/pnpm/pnpm/releases/tag/v12.24.0)

### undici 8.14.0: deduplicate không gộp request có body, retry có option `resume`
Bản ra ngày 27/11. undici là HTTP client nằm dưới `fetch` của Node.js, và nhiều SDK dùng trực tiếp.

- **`interceptors.deduplicate`** không còn gộp các request có body (#6240). Docs giải thích lý do: body không nằm trong deduplication key, nên hai request khác body có thể bị gộp nhầm thành một và nhận chung response.
- **`retry` có option `resume`** (mặc định `true`, #6096). Khi đặt `false`, response lỗi sau khi đã nhận header sẽ không được nối tiếp bằng request `Range`; lỗi đi thẳng về handler, chỉ lỗi trước khi có header mới được retry. Docs ghi option này hợp với proxy stream response xuống client ngay khi nhận.
- **`decompress`** thêm option `preserveHeaders` (#6239).
- HTTP/1 destroy socket khi lỗi (#6255); HTTP/2 reset stream bị abort bằng `CANCEL` (#6201) và giữ AsyncLocalStorage context cho body chunk (#6209).

Áp dụng: nếu bạn viết một BFF hoặc proxy bằng Node.js stream file từ service khác về client, `resume: false` tránh trường hợp retry nối thêm byte vào một response đã gửi dở. Bản fix AsyncLocalStorage trên HTTP/2 giúp request id trong log không bị mất khi xử lý body.

Nguồn: [undici v8.14.0](https://github.com/nodejs/undici/releases/tag/v8.14.0), [undici Interceptors docs](https://github.com/nodejs/undici/blob/v8.14.0/docs/docs/api/Interceptors.md)

### Vite 8.4.0: `server.fs.strict: 'extended'`, plugin name trong error, `css.devSourcemap` đổi chỗ
Bản ra ngày 26/11.

- **`server.fs.strict: 'extended'`**: theo docs, giá trị này áp dụng thêm kiểm tra truy cập file cho các module được plugin `load`, trừ ID bắt đầu bằng `\0`. Trước đây kiểm tra chỉ áp lên file serve qua dev server, plugin load file ngoài workspace thì lọt.
- **Safe module**: thêm `environment.addSafeModule`, `safeModulePaths` tách riêng theo environment, đăng ký thêm tham chiếu từ HTML.
- **Error message có tên plugin** cho hook và module hook, đỡ phải đoán plugin nào làm hỏng build.
- **`css.devSourcemap` chuyển sang `dev.sourcemap.css`**.
- Worker chunk có trong build manifest, build retry CSS preload thất bại, `--configLoader` được ổn định và `--configLoader=runner` bị deprecate.

Áp dụng: dev server Vite từng nhiều lần dính lỗi đọc file tùy ý khi bị expose ra mạng (`--host`). Với dự án React hoặc Vue chạy dev server trong container hoặc VPS dev dùng chung, bật `'extended'` là thêm một lớp chặn. Nhớ đổi `css.devSourcemap` trong config.

Nguồn: [Vite v8.4.0](https://github.com/vitejs/vite/releases/tag/v8.4.0), [Vite server options](https://github.com/vitejs/vite/blob/v8.4.0/docs/config/server-options.md)

### httpx 0.29.0: tối thiểu Python 3.10, `FunctionAuth` thành public API
Bản ra ngày 26/11. Hai thay đổi: bỏ Python 3.9 (#3832) và export `FunctionAuth` (#3699). Không có thay đổi nào được ghi là breaking, nhưng httpx là dependency của rất nhiều SDK (OpenAI, Anthropic) và test client của FastAPI, nên service còn chạy Python 3.9 sẽ không resolve được 0.29.

Áp dụng: nếu Docker image FastAPI còn dùng `python:3.9`, đây là lúc chuyển lên 3.11 trở lên; FastAPI 0.164+ cũng đã yêu cầu Python 3.11+. Ghim `httpx<0.29` chỉ là giải pháp tạm.

### undici 8.14: retry và deduplicate cho HTTP client nội bộ (cần Node.js 22.19.0+)

```bash
npm install undici@8.14.0
```

```js
import { Agent, interceptors, setGlobalDispatcher } from 'undici'

const agent = new Agent().compose(
  interceptors.retry({
    maxRetries: 5,
    minTimeout: 200,
    maxTimeout: 5000,
    timeoutFactor: 2,
    statusCodes: [429, 502, 503, 504],
    resume: false // 8.14+: không nối tiếp response đã nhận header bằng Range
  }),
  interceptors.deduplicate({
    methods: ['GET'],
    excludeHeaderNames: ['x-request-id']
  })
)

setGlobalDispatcher(agent)
```

Ví dụ retry lấy từ docs Interceptors, `resume` theo docs RetryHandler, các option của `deduplicate` theo docs cùng trang. Thứ tự compose có ý nghĩa: interceptor cuối danh sách được gọi đầu tiên.

## Góc học sâu

### Exception trên hot path: vì sao một cái 404 lại tốn CPU
Bản vá 404 của NestJS là ví dụ tốt về một chi phí ít ai để ý: tạo một `Error` trong V8 không chỉ là cấp phát object. Lúc constructor chạy, engine đi ngược call stack để ghi lại các frame (mặc định tối đa `Error.stackTraceLimit = 10` frame). Framework như NestJS có call stack sâu qua middleware, guard, interceptor, pipe, nên capture stack trace là phần đáng kể trong chi phí xử lý một request lỗi.

Với lỗi thật, stack trace đáng giá vì nó giúp debug. Với "lỗi" thuộc luồng nghiệp vụ bình thường, nó là lãng phí:

- 404 cho route không tồn tại, nhất là khi bị bot quét hàng nghìn path.
- Validation fail (400) trên endpoint public.
- 401 do token hết hạn, xảy ra liên tục theo chu kỳ.

Ba hướng xử lý, từ nhẹ đến mạnh:

1. **Không throw cho luồng dự đoán được.** Trong service layer, trả về kết quả dạng `{ ok: false, reason }` hoặc `null` rồi để controller map sang HTTP status, thay vì throw rồi catch ở filter.
2. **Exception class không cần stack.** Với class lỗi chỉ dùng để mang status code, có thể bỏ capture stack như NestJS vừa làm cho 404. Đổi lại, log của lỗi đó sẽ không có stack, nên chỉ làm với lỗi bạn chắc chắn không cần debug.
3. **Rate limit trước khi tới framework.** 404 rẻ nhất là 404 không bao giờ chạm tới Node.js: chặn ở nginx hoặc dùng rate limiter theo IP cho các path lạ.

Cách đo: chạy `autocannon` hoặc `k6` bắn vào một path không tồn tại, so sánh requests per second và CPU trước và sau khi nâng NestJS 12.6.3. Nếu chênh lệch rõ, hãy tìm các chỗ khác trong code đang throw cho luồng bình thường.

Nguồn tham khảo: [Node.js Errors: error.stackTraceLimit](https://nodejs.org/api/errors.html#errorstacktracelimit)

## Tối ưu dùng AI

### Chủ đề hôm nay: dùng agent để đọc hiểu một codebase lạ, hỏi từ rộng đến hẹp và đòi chỉ ra file
Intern mới vào dự án thường mất cả tuần chỉ để hiểu request đi qua những đâu. Coding agent rút ngắn việc này rất tốt, với điều kiện bạn hỏi có trình tự và bắt nó chỉ ra bằng chứng trong code thay vì kể chung chung. Mục "Understand new codebases" trong Claude Code docs gợi ý hai quy trình.

**Quy trình 1: tổng quan trước, chi tiết sau.** Mở agent ở thư mục gốc dự án và đi theo thứ tự:

1. Hỏi tổng quan: `give me an overview of this codebase`.
2. Hỏi kiến trúc: `explain the main architecture patterns used here`.
3. Hỏi dữ liệu: `what are the key data models?`.
4. Hỏi một mối quan tâm xuyên suốt: `how is authentication handled?`.

Docs khuyên thêm: bắt đầu bằng câu hỏi rộng rồi thu hẹp, hỏi về coding convention và pattern của dự án, và yêu cầu một glossary thuật ngữ riêng của dự án.

**Quy trình 2: lần theo một tính năng.**

1. `find the files that handle user authentication`
2. `how do these authentication files work together?`
3. `trace the login process from front-end to database`

Docs nhấn mạnh dùng đúng ngôn ngữ domain của dự án ("đơn hàng", "tenant", "ví") thay vì từ chung chung, và cài code intelligence plugin cho ngôn ngữ của bạn để agent có "go to definition" và "find references" chính xác.

**Ba điều chỉnh để câu trả lời đáng tin hơn:**

- **Đòi trích dẫn vị trí.** Thêm vào câu hỏi: mỗi khẳng định phải kèm `file:line`. Câu trả lời không có vị trí là câu bạn chưa kiểm được.
- **Dùng subagent cho phần khám phá rộng.** Docs Claude Code gợi ý `use a subagent to investigate how our auth system handles token refresh`: subagent đọc file trong context riêng và chỉ gửi về bản tóm tắt, context chính của bạn không bị lấp đầy bởi hàng chục file.
- **Ghi lại kết quả.** Những gì agent phải mất công tìm ra (lệnh chạy test, nơi đặt migration, quy ước đặt tên) là thứ nên vào CLAUDE.md hoặc AGENTS.md, để session sau không phải khám phá lại.

Template prompt cho buổi onboarding với một dự án NestJS hoặc Laravel:

```text
I just joined this project as a backend developer. Do not edit any files.

Trace what happens when a client calls POST /orders, from the HTTP entry point to the database write. For each step, name the file and line, the function, and what it does in one sentence. Include middleware, guards or policies, validation, the service layer, the repository or ORM call, and any queued job or event fired afterward.

Then list the 5 project-specific terms I need to know to read this flow, with a one-line definition each and where each is defined.

If something is unclear or you are guessing, say so explicitly instead of filling the gap.
```

Checklist khi đọc câu trả lời:

- Mở thử 2 hoặc 3 vị trí `file:line` agent đưa ra. Nếu một chỗ sai, hỏi lại trước khi tin phần còn lại.
- Có bước nào agent đánh dấu là đoán không? Đó là chỗ nên hỏi senior trong team.
- Luồng có nhắc tới job, event hoặc listener không? Đây là phần hay bị bỏ sót khi chỉ đọc controller.

Nguồn: [Claude Code common workflows: Understand new codebases](https://code.claude.com/docs/en/common-workflows), [Claude Code best practices](https://code.claude.com/docs/en/best-practices)

### Áp dụng ngay hôm nay
Chọn một endpoint bạn sắp phải sửa trong dự án đang làm. Chạy template trên ở plan mode (`claude --permission-mode plan`) hoặc nói rõ không sửa file, rồi mở kiểm tra 3 vị trí `file:line` trong câu trả lời. Chép các bước đúng và glossary vào một file ghi chú trong repo, hoặc gợi ý team đưa phần cốt lõi vào CLAUDE.md.
