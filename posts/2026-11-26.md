# Tech Radar 26/11/2026: NestJS 12.6.2 thêm nack về dead letter cho RabbitMQ, redis-py 8.2 cho chọn key nào được cache phía client

> NestJS ra hai bản patch trong một ngày, đáng chú ý nhất là tùy chọn `nackOnInternalError` cho RabbitMQ và yêu cầu Node.js mới hơn cho adapter Fastify. redis-py 8.2 thêm tracking mode OPTIN/OPTOUT cho client-side caching và bỏ Python 3.10. Ai dùng Livewire PowerGrid với `naturalSort` cần nâng ngay vì có SQL injection.

## Điểm nóng hôm nay

### NestJS 12.6.1 và 12.6.2: RabbitMQ đẩy message lỗi sang dead letter exchange, Fastify adapter cần Node.js 20.19+ hoặc 22.12+
Cả hai bản ra ngày 25/11, kèm bản backport 11.2.12 cho nhánh 11.

Những điểm nên biết:

- **`nackOnInternalError` cho RabbitMQ** (mặc định `false`): khi bật cùng `noAck: false`, handler nào ném lỗi không phải `RpcException` sẽ bị `nack(message, false, false)`, tức không requeue, message đi sang dead letter exchange của queue. Trước đây message lỗi nằm unacked cho tới khi channel đóng. Request vẫn nhận reply lỗi như cũ. Handler thành công không được tự ack, bạn vẫn phải ack.
- **Lưu ý với ValidationPipe**: mặc định pipe ném `BadRequestException`, bị coi là lỗi internal nên cũng bị dead-letter. Nếu muốn coi lỗi validation là lỗi nghiệp vụ, truyền `exceptionFactory` trả về `RpcException`.
- **RabbitMQ sau reconnect**: 12.6.2 nack delivery thất bại trên đúng channel gốc của nó.
- **Fastify adapter**: từ `@fastify/middie` 9.3.7 (đi kèm `@nestjs/platform-fastify` 12.6.0), adapter cần Node.js 20.19+ hoặc 22.12+, vì middie `require()` module ESM `path-to-regexp` 9. Bản 11.2.12 cũng mang yêu cầu này; bản Node 20.x hay 22.x cũ hơn sẽ lỗi `ERR_REQUIRE_ESM`.
- **Hardening**: trên Express, multipart field name đặt key `__proto__` hoặc path `constructor[prototype]` trong `req.body` bị trả 400. `ConsoleLogger` redact thêm `Headers`, `URLSearchParams`, `FormData` và username, password, query của `URL`.
- 12.6.2 sửa regression của 12.6.1 làm `applyDecorators()` sai kiểu, và `res.send()` giờ pipe được `Readable` stream.

Áp dụng: nếu service NestJS consume RabbitMQ với `noAck: false`, đây là cách gọn để message lỗi không kẹt trong trạng thái unacked mà vào DLX để điều tra và replay. Trước khi nâng, kiểm tra `node -v` trên image Docker và VPS nếu bạn dùng Fastify adapter. Nếu đang ở 12.6.1, nhảy thẳng lên 12.6.2 vì regression của `applyDecorators()`.

Nguồn: [NestJS v12.6.2](https://github.com/nestjs/nest/releases/tag/v12.6.2), [NestJS v12.6.1](https://github.com/nestjs/nest/releases/tag/v12.6.1), [NestJS v11.2.12](https://github.com/nestjs/nest/releases/tag/v11.2.12), [PR #18686](https://github.com/nestjs/nest/pull/18686)

### redis-py 8.2.0: tracking mode cho client-side caching, routing cluster theo tip của server, bỏ Python 3.10
Ra ngày 23/11. Thay đổi chính:

- `CacheConfig` có thêm `tracking_mode` (`PLAIN`, `OPTIN`, `OPTOUT`) và `cache_predicate(command, keys)`. `PLAIN` giữ hành vi cũ: server nhớ mọi key đã đọc trên connection có cache. `OPTIN` chỉ track những read đi kèm `CLIENT CACHING YES`, hợp khi bạn chỉ cache một nhóm key nhỏ. `OPTOUT` track mọi thứ trừ những read đi kèm `CLIENT CACHING NO`.
- `CacheConfig.DEFAULT_ALLOW_LIST` và `READ_COMMANDS` bị deprecate và không còn được đọc. Việc lệnh nào được cache giờ do metadata resolver quyết định. Code nào chỉnh hai danh sách này sẽ không còn tác dụng.
- Cluster: lệnh multi-shard được tách theo slot, retry chỉ gửi lại phần chưa có reply. Topology refresh được gộp và giới hạn tần suất, tham số mới `topology_refresh_min_interval` mặc định 1 giây.
- Lệnh mới cho Redis 8.12: TTL từng member của Set (`sexpire`, `sttl`, `spersist`, `saddex`...) và `zmove`, `bzmove` cho sorted set.
- Nếu `HELLO` bị server hoặc proxy từ chối và bạn không đặt protocol rõ ràng, client tự quay về RESP2. README ghi rằng fallback này chỉ áp dụng cho callback của lệnh core; với lệnh module (JSON, Search...) qua proxy không hỗ trợ `HELLO` thì đặt `protocol=2` tường minh.
- Bảo mật: redact credential trong lỗi pipeline và cluster routing, token của lock sinh bằng `uuid4`.
- Python 3.10 bị bỏ; theo README, bản cuối hỗ trợ 3.10 là 8.1.x.

Áp dụng: service FastAPI hay worker Celery dùng client-side caching cho dữ liệu đọc nhiều (profile, config) có thể chuyển sang `OPTIN` để server không phải nhớ hàng triệu key không bao giờ được cache, giảm bộ nhớ tracking và lượng invalidation message.

Nguồn: [redis-py releases](https://github.com/redis/redis-py/releases), [redis-py README](https://github.com/redis/redis-py/blob/master/README.md), [redis-py: RESP3 features và tracking modes](https://github.com/redis/redis-py/blob/master/docs/resp3_features.rst)

### Nuxt 4.7.0: thử Nitro v3, validate runtimeConfig bằng schema, error boundary khi SSR
Ra ngày 23/11. Điểm đáng chú ý cho người làm fullstack:

- **Validated runtime config**: mỗi giá trị trong `runtimeConfig` có thể là một Standard Schema (ví dụ Zod). Giá trị sai hoặc thiếu làm server không khởi động và báo một lỗi gộp. Đây là thứ trước đây phải tự viết bằng một file kiểm tra env riêng.
- **Nitro v3 preview**: thêm package `nitro` vào dependencies để build Nuxt 4 bằng Nitro v3, nền của Nuxt 5. Release ghi rõ là "highly experimental", chỉ nên thử trên branch. Khi bật, route rule `/blog/*` sẽ match cả `/blog/2026/hello`, rule có nhiều wildcard như `/api/*/items/**` làm build lỗi, và server code import package không khai báo trong `package.json` sẽ lỗi.

- **Template diagnostics**: cảnh báo `<NuxtLink>` có `to` tĩnh không trỏ tới page nào (`NUXT_B4025`).
- Theo số liệu trong release, server output của starter giảm 43% (2,17 MB xuống 1,23 MB) so với 4.6.4.

Áp dụng: nếu frontend Nuxt deploy lên VPS bằng Docker, validate runtime config giúp container chết ngay khi thiếu `NUXT_PUBLIC_API_BASE` thay vì chạy lên rồi lỗi ở request đầu tiên. Nitro v3 thì để thử trên branch riêng, kiểm tra các route rule có wildcard trước.

## Cài đặt và dùng thử

### NestJS: consumer RabbitMQ đẩy message lỗi sang DLX (cần NestJS 12.6.1+, nên dùng 12.6.2)
Package transport RabbitMQ theo docs NestJS:

```bash
npm i --save amqplib amqp-connection-manager
npm i @nestjs/core@12.6.2 @nestjs/common@12.6.2 @nestjs/microservices@12.6.2
```

Cấu hình lấy từ PR #18686:

```typescript
app.connectMicroservice<MicroserviceOptions>({
  transport: Transport.RMQ,
  options: {
    urls: ['amqp://localhost:5672'],
    queue: 'orders',
    noAck: false,
    nackOnInternalError: true,
    queueOptions: {
      durable: true,
      arguments: { 'x-dead-letter-exchange': 'orders.dlx' },
    },
  },
});
```

Hai điều cần nhớ: exchange `orders.dlx` và queue bind vào nó phải tồn tại, nếu không broker sẽ bỏ message bị nack. Và `x-dead-letter-exchange` là argument lúc khai báo queue; nếu queue `orders` đã tồn tại với argument khác, RabbitMQ sẽ từ chối khai báo lại, nên với queue đang chạy, cân nhắc đặt DLX bằng policy phía broker thay vì đổi code.

### redis-py 8.2: chỉ cache key `user:*` phía client (cần Python 3.11+)

```bash
pip install -U redis
```

Ví dụ từ docs của redis-py:

```python
import redis
from redis.cache import CacheConfig, TrackingMode
from redis.utils import str_if_bytes

r = redis.Redis(host='localhost', port=6379, protocol=3,
                cache_config=CacheConfig(
                    tracking_mode=TrackingMode.OPTIN,
                    cache_predicate=lambda command, keys: str_if_bytes(keys[0]).startswith('user:'),
                ))
r.get('user:42')    # miss: CLIENT CACHING YES + GET; lưu vào cache, được track
r.get('user:42')    # hit: không gửi gì lên server
r.get('session:9')  # gửi bình thường; không cache, không track
```

Lưu ý từ docs: `OPTIN` mà không có `cache_predicate` thì không cache gì cả (client sẽ cảnh báo). Truyền `tracking_mode` dạng string như `"optin"` sẽ bị `TypeError`, phải dùng enum `TrackingMode`. `cache_predicate` đi với `PLAIN` sẽ bị bỏ qua kèm cảnh báo.

## Bảo mật cần để ý

### power-components/livewire-powergrid: SQL injection qua `sortDirection` (GHSA-7fgc-3h6c-698r, High)
- **Bị ảnh hưởng**: `>= 6.0.0, < 6.10.4`. **Đã vá**: 6.10.4.
- **Điều kiện**: bảng PowerGrid có cột dùng `naturalSort`. Property public `sortDirection` của Livewire được chèn nguyên văn vào `orderByRaw`, không giới hạn ở `asc`/`desc`. Kẻ tấn công gửi `POST /livewire/update` với `sortField` rỗng để bỏ qua validation direction của Laravel, rồi đặt `sortDirection` tùy ý.
- **Tác động**: advisory đánh giá chủ yếu là đọc dữ liệu, vì driver PDO MySQL mặc định chặn stacked query.
- **Làm gì**: `composer update power-components/livewire-powergrid` lên 6.10.4. Advisory không nêu workaround.

Bài học chung cho Laravel: mọi public property của Livewire đều do client điều khiển. Giá trị nào đi vào `orderByRaw`, `whereRaw` hay tên cột phải được whitelist, không chỉ validate kiểu.

### i18next: DoS qua `addResourceBundle` với deep merge (GHSA-6jcc-5g8w-32mx, Moderate)
- **Bị ảnh hưởng**: `< 26.3.4`. **Đã vá**: 26.3.4.
- **Điều kiện**: ứng dụng gọi `addResourceBundle(lng, ns, data, deep, overwrite)` với `deep: true`, `overwrite: true` và `data` do người dùng kiểm soát. `deepExtend` kiểm tra key bằng toán tử `in` nên đi theo prototype chain, key như `hasOwnProperty` làm nó ghi đè thuộc tính của built-in dùng chung, khiến cả process hỏng. Advisory ghi rằng không backend hay integration chuẩn nào của i18next gọi theo cách này.
- **Làm gì**: nâng lên 26.3.4. Nếu app Next.js hoặc Node của bạn merge bản dịch tải từ CMS hay từ người dùng bằng `addResourceBundle`, ưu tiên nâng sớm.

## Góc học sâu

### Ack, nack và dead letter: vì sao message lỗi không nên nằm im ở trạng thái unacked
Với RabbitMQ ở chế độ manual ack (`noAck: false`), mỗi message giao cho consumer có ba kết cục:

| Thao tác | Ý nghĩa | Khi nào dùng |
|---|---|---|
| `ack` | Xử lý xong, broker xóa message | Handler thành công |
| `nack` có requeue | Trả về queue để giao lại | Lỗi tạm thời (DB timeout, dịch vụ ngoài chết) |
| `nack` không requeue | Bỏ khỏi queue; nếu queue có DLX thì chuyển sang đó | Lỗi không tự hết (payload sai, bug) |

Nếu không làm gì cả, message nằm ở trạng thái unacked. Nó chiếm một slot `prefetch` của consumer, nên đủ số message lỗi kiểu này là consumer ngừng nhận việc mới dù process vẫn sống. Khi channel hay connection đóng, broker giao lại toàn bộ message unacked, và nếu lỗi là do payload, nó lại lỗi tiếp. Đây chính là tình huống `nackOnInternalError` của NestJS giải quyết.

Hai chi tiết hay gây bug:

1. **Delivery tag gắn với channel.** Tag chỉ có nghĩa trên channel đã giao message. Ack hoặc nack bằng channel khác (thường xảy ra sau reconnect) bị broker coi là lỗi giao thức và đóng channel. Bản 12.6.2 sửa đúng chỗ này. Tương tự, settle một message hai lần cũng làm channel bị đóng, nên PR của NestJS bỏ qua nack nếu bạn đã tự ack hoặc reject.
2. **Requeue vô hạn tạo poison message.** Message lỗi do dữ liệu mà luôn requeue sẽ quay vòng mãi, đốt CPU và log. Cách phổ biến: requeue cho lỗi tạm thời có giới hạn số lần, còn lại nack không requeue để vào DLX, có alert theo độ dài queue DLX và một script replay sau khi sửa bug.

Vì broker có thể giao lại (sau reconnect, sau requeue, sau replay từ DLX), mô hình này là at-least-once. Consumer phải idempotent: lưu message id hoặc business key đã xử lý trong bảng có unique constraint, hoặc thiết kế thao tác sao cho chạy hai lần cho cùng kết quả. BullMQ trên Redis, SQS hay Kafka đều có biến thể của cùng ý tưởng: retry có giới hạn, chỗ chứa message chết, và consumer idempotent.

### Chủ đề hôm nay: điều khiển định dạng output khi gọi LLM từ backend, nói điều cần làm thay vì điều cấm
Khi backend gọi model để sinh text cho người dùng (email thông báo, tóm tắt ticket, mô tả sản phẩm), lỗi hay gặp nhất không phải nội dung sai mà là định dạng sai: Markdown lọt vào email plain text, bullet vụn vặt, câu mở đầu "Here is the summary:". Tài liệu prompting của Claude đưa ra bốn cách điều khiển:

1. **Nói điều cần làm thay vì điều cấm.** Thay vì "Do not use markdown", viết "Your response should be composed of smoothly flowing prose paragraphs." Câu cấm vẫn đưa khái niệm markdown vào context; câu mô tả cho model một đích rõ ràng.
2. **Dùng tag XML làm chỉ báo định dạng.** Ví dụ yêu cầu viết phần văn xuôi trong tag `<smoothly_flowing_prose_paragraphs>`. Ở backend, tag còn giúp bạn cắt đúng phần cần lấy bằng code.
3. **Cho style của prompt khớp với style output mong muốn.** Prompt viết toàn bullet và heading Markdown thì output cũng có xu hướng nhiều Markdown. Muốn output văn xuôi, viết prompt bằng văn xuôi.
4. **Chỉ dẫn chi tiết khi có yêu cầu cụ thể**, ví dụ khi nào được dùng list và khi nào không.

Thêm hai điểm từ cùng tài liệu: từ Claude 4.6 trở đi, prefill (gửi sẵn một đoạn assistant message cuối để model viết tiếp) không còn được hỗ trợ và trả lỗi 400. Muốn bỏ câu mở đầu, dùng chỉ dẫn trực tiếp trong system prompt; muốn JSON đúng schema, dùng structured outputs (đã nói ở bản tin trước). Và nếu model đôi khi vẫn chèn câu mở đầu, tài liệu khuyên cắt bỏ bằng post-processing thay vì cố ép bằng prompt.

Template system prompt cho một endpoint sinh email thông báo:

```text
You write the body of transactional emails for an online store. The body is sent as plain text, so it must read naturally without any formatting.

Write two or three short paragraphs of flowing prose. Mention the order number and the next step the customer should take. Put the body inside <email_body> tags and write nothing outside those tags.

Respond directly without preamble. Do not start with phrases like "Here is..." or "Based on...".
```

Phía code chỉ lấy nội dung trong tag, và có fallback khi tag không có:

```typescript
function extractEmailBody(text: string): string | null {
  const m = text.match(/<email_body>([\s\S]*?)<\/email_body>/);
  return m ? m[1].trim() : null; // null: log lại và retry hoặc dùng template tĩnh
}
```

Checklist khi output định dạng sai:

- Prompt có đang cấm thay vì mô tả đích không? Viết lại thành câu khẳng định.
- Prompt có đầy Markdown trong khi bạn muốn plain text không? Viết lại bằng văn xuôi.
- Output có cần máy đọc không? Nếu có, dùng structured outputs hoặc tool có enum, đừng dựa vào regex trên văn xuôi.
- Còn dùng prefill ở assistant turn cuối không? Đổi sang chỉ dẫn trong system prompt trước khi chuyển sang model mới.

Nguồn: [Claude prompting best practices: Output and formatting](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)

### Áp dụng ngay hôm nay
Mở một prompt đang dùng trong code có câu dạng "Do not..." liên quan tới định dạng. Viết lại thành câu mô tả output mong muốn, bọc phần cần lấy trong một tag XML, sửa hàm parse để lấy nội dung trong tag và log khi không tìm thấy. Chạy 5 input mẫu trước và sau, so sánh bằng mắt số lần Markdown hoặc câu mở đầu lọt ra.
