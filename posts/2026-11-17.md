# Tech Radar 17/11/2026: FastAPI 0.163 thêm `Depends(max_concurrency=...)`, Mongoose vá lỗ hổng bypass `sanitizeFilter` trên cả 4 nhánh

> Tin đáng làm ngay hôm nay: nếu service Node.js của bạn dùng Mongoose với `sanitizeFilter` để chặn query selector injection, hãy nâng lên 9.12.2, 8.24.10, 7.8.14 hoặc 6.13.13 vì bản cũ để lọt một số operator `$` ở top-level filter. Với dân FastAPI, 0.163.0 cho phép giới hạn số request dùng một dependency cùng lúc, cách gọn để không làm cạn connection pool. Thêm NestJS 12.5.1 có graceful shutdown cho các transport microservice và SQLAlchemy 2.1.9 sửa lỗi LATERAL trả sai dòng.

## Điểm nóng hôm nay

### FastAPI 0.163.0: `Depends(max_concurrency=...)` giới hạn số lần dependency chạy song song
FastAPI 0.163.0 (14/11) thêm tham số `max_concurrency` cho `Depends()`. Bản 0.163.1 (15/11) sửa OpenAPI cho response model có nested computed field. Cả hai yêu cầu Python 3.11 trở lên (3.10 đã bị bỏ từ 0.162.6).

Ý tưởng: khi nhiều request cùng cần một tài nguyên có giới hạn (connection pool của database là ví dụ docs dùng), bạn đặt trần cho dependency tạo ra tài nguyên đó:

```python
SessionDep = Annotated[Session, Depends(get_session, max_concurrency=5)]
```

Những điểm docs nhấn mạnh, cần đọc kỹ trước khi dùng:

- Request thứ sáu sẽ chờ, và trong lúc chờ **không chiếm worker thread**, nên threadpool vẫn rảnh cho việc khác.
- Muốn nhiều route chia chung một giới hạn thì phải dùng lại **cùng một object `Depends()`**, ví dụ một alias `Annotated`. Viết `Depends(get_session, max_concurrency=5)` mới ở mỗi route là mỗi route một giới hạn riêng, dù chung function.
- Dependency có `yield` giữ slot đến khi phần cleanup sau `yield` chạy xong. Với `scope="request"` (mặc định) thì đó là sau khi response đã gửi; với `scope="function"` là trước khi gửi response.
- Giới hạn tính theo từng worker process và từng event loop. Chạy 4 worker với `max_concurrency=5` nghĩa là tối đa 20 session trên toàn máy, FastAPI không biết pool size của bạn.
- Giá trị cache trong cùng request không bị tính thêm lần nữa.

Áp dụng: API FastAPI chạy sau Gunicorn/Uvicorn nhiều worker trên VPS, Postgres có `max_connections` thấp. Thay vì để request ồ ạt mượn connection rồi timeout ở tầng pool, bạn chặn sớm ở tầng dependency. Xem phần Góc học sâu về rủi ro deadlock khi một request cần hai slot.

Nguồn: [FastAPI release notes](https://github.com/fastapi/fastapi/blob/master/docs/en/docs/release-notes.md), [Advanced Dependencies: Limit dependency concurrency](https://github.com/fastapi/fastapi/blob/master/docs/en/docs/advanced/advanced-dependencies.md)

### Mongoose 9.12.2, 8.24.10, 7.8.14, 6.13.13: chặn bypass `sanitizeFilter`
Ngày 16/11 Mongoose phát hành đồng loạt bốn nhánh với cùng dòng changelog: "make sanitizeFilter catch any fields that start with $ in top-level filter to avoid bypass using $_internalSchemaXor and other MongoDB internal expressions", kèm "hardening for sanitizeProjection". Nhánh 6.x còn thêm fix `isBsonType` bỏ qua thuộc tính `_bsontype` do người dùng truyền vào.

`sanitizeFilter` là option Mongoose đưa ra từ bản 6 để chống query selector injection: object lồng có key bắt đầu bằng `$` trong filter sẽ bị bọc trong `$eq`, nên `{ pwd: { $ne: null } }` thành so sánh bằng chứ không còn là operator. Vấn đề là một số key `$` nằm ngay ở top-level filter, như expression nội bộ `$_internalSchemaXor` của MongoDB, đi lọt qua. Trong code hiện tại trên nhánh master, mọi key top-level bắt đầu bằng `$` ngoài `$and`, `$or`, `$nor` sẽ ném `MongooseError` "... is not allowed with sanitizeFilter".

Áp dụng: kiểm tra mọi chỗ bạn truyền `req.body` hoặc `req.query` thẳng vào `find()`, `findOne()`, `countDocuments()`. Nếu bạn đang dựa vào `sanitizeFilter` làm lớp phòng thủ chính, đây là bản nên nâng ngay. Chi tiết ở mục Bảo mật.

Nguồn: [Mongoose CHANGELOG](https://github.com/Automattic/mongoose/blob/master/CHANGELOG.md), [Migrating to 6: sanitizeFilter and trusted()](https://github.com/Automattic/mongoose/blob/master/docs/migrating_to_6.md)

### NestJS 12.5.1: graceful shutdown cho RMQ, TCP, MQTT, Redis, NATS server
Bản patch ngày 16/11 sau đợt 12.5.0 hôm 14/11. Nhóm thay đổi đáng chú ý nhất là graceful shutdown cho các server microservice: RMQ (#18525), TCP (#18514), MQTT (#18513), Redis và NATS (#18505). Ngoài ra:

- `core`: root module có thể khai báo bằng module metadata (#18523).
- `common`: `ParseDatePipe` từ chối ngày vượt quá số ngày của tháng, ví dụ 31/02 (#18515).
- `microservices`: decode đúng từng giá trị của Kafka header lặp lại (#18521); ngừng thử kết nối Kafka khi client đã đóng (#18512).

Áp dụng: nếu bạn chạy worker NestJS tiêu thụ RabbitMQ hoặc Redis trong Docker, mỗi lần deploy container nhận SIGTERM. Graceful shutdown ở tầng transport giúp message đang xử lý dở được làm xong thay vì bị cắt ngang. Vẫn nhớ bật `app.enableShutdownHooks()` và để `stop_grace_period` của Compose đủ dài. Với `ParseDatePipe`, request trước đây lọt qua với ngày không tồn tại giờ sẽ nhận 400, nên chạy lại test API có trường ngày.

Nguồn: [NestJS v12.5.1 release](https://github.com/nestjs/nest/releases/tag/v12.5.1)

### SQLAlchemy 2.1.9: LATERAL mất correlation trả sai dòng, `mappings()` nhanh hơn
SQLAlchemy 2.1.9 và 2.0.58 cùng ra ngày 16/11. Trong 2.1.9:

- Sửa regression: relationship tới aliased class dựa trên correlated LATERAL subquery, load bằng `joinedload` trong query có `DISTINCT` hoặc `GROUP BY`, render LATERAL **thiếu correlation và trả về dòng sai** (#13783). Một fix đi kèm (#13786) xử lý cùng lỗi với `selectinload`, `subqueryload`, `lazyload`, `immediateload`.
- `Result.mappings()` và `AsyncResult.mappings()` nhanh hơn rõ khi có Cython extension, vì việc chuyển `Row` sang `RowMapping` giờ chạy trong code đã compile (#13769).
- Sửa regression: ORM mapped dataclass dùng `orm_insert_sentinel` hoặc `mapped_column` với default là `ColumnDefault`/`Sequence` không flush được (#13788).

Áp dụng: lỗi "trả sai dòng mà không báo lỗi" là loại nguy hiểm nhất. Nếu FastAPI service của bạn dùng relationship qua LATERAL (thường gặp ở query "top N item mỗi nhóm"), nâng lên và thêm test so sánh kết quả. Endpoint trả về `result.mappings().all()` cho JSON cũng hưởng lợi về hiệu năng.

Nguồn: [SQLAlchemy changelog 2.1](https://github.com/sqlalchemy/sqlalchemy/blob/main/doc/build/changelog/changelog_21.rst)

## Cài đặt và dùng thử

### FastAPI 0.163: chặn cạn connection pool bằng `max_concurrency` (cần Python 3.11+)
Cài theo README chính thức:

```bash
uv add "fastapi[standard]"
uv run fastapi dev
```

Ví dụ tối thiểu dựa trên tutorial SQL databases của FastAPI, thêm `max_concurrency` khớp với pool size. `pool_size` và `max_overflow` là tham số chuẩn của `create_engine`; đặt `max_overflow=0` để con số trong pool là con số thật:

```python
from typing import Annotated

from fastapi import Depends, FastAPI
from sqlalchemy import text
from sqlmodel import Session, create_engine

engine = create_engine(
    "postgresql+psycopg://app:secret@localhost:5432/app",
    pool_size=5,
    max_overflow=0,
)


def get_session():
    with Session(engine) as session:
        yield session


# Một alias dùng chung cho mọi route, để mọi route chia chung 5 slot
SessionDep = Annotated[Session, Depends(get_session, max_concurrency=5)]

app = FastAPI()


@app.get("/health/db")
def health_db(session: SessionDep):
    session.exec(text("SELECT 1"))
    return {"ok": True}
```

Thử tải bằng `hey` hoặc `ab` với 50 kết nối đồng thời: trước khi có giới hạn bạn sẽ thấy lỗi `QueuePool limit ... timed out` ở tầng SQLAlchemy khi request chờ quá `pool_timeout`; sau khi có giới hạn, request xếp hàng ở tầng FastAPI. Nhớ trừ hao: nếu background job hay endpoint khác cũng dùng `engine` này mà không qua `SessionDep`, hãy để `max_concurrency` nhỏ hơn pool size.

### Nâng Mongoose lên bản đã vá
Chọn đúng nhánh major bạn đang dùng:

```bash
npm ls mongoose
npm install mongoose@9.12.2   # nhánh 9.x
npm install mongoose@8.24.10  # nhánh 8.x
npm install mongoose@7.8.14   # nhánh 7.x
npm install mongoose@6.13.13  # nhánh 6.x
```

Cách bật `sanitizeFilter` theo docs, toàn cục hoặc theo từng query:

```javascript
mongoose.set('sanitizeFilter', true);

// hoặc từng query
const docs = await MyModel.find({ name: req.query.name, age: req.query.age })
  .setOptions({ sanitizeFilter: true });
```

Sau khi nâng, query nào cố ý dùng operator ở top-level (ví dụ `$expr`) từ input tin cậy sẽ cần bọc bằng `mongoose.trusted()` hoặc tắt option cho riêng query đó, nếu không sẽ nhận lỗi "is not allowed with sanitizeFilter".

## Bảo mật cần để ý

### Mongoose: bypass `sanitizeFilter` qua operator `$` ở top-level filter
- **Ảnh hưởng**: ứng dụng dùng Mongoose bật `sanitizeFilter` và đưa input người dùng vào filter. Mọi bản trước 9.12.2, 8.24.10, 7.8.14, 6.13.13 trên từng nhánh tương ứng.
- **Đã vá**: 9.12.2, 8.24.10, 7.8.14, 6.13.13 (cùng ngày 16/11/2026).
- **Bản chất**: một số expression nội bộ của MongoDB như `$_internalSchemaXor` đặt ở top-level filter lọt qua lớp sanitize. Kèm theo là hardening cho `sanitizeProjection`.
- **Ghi chú**: changelog không ghi mã CVE hay GHSA tại thời điểm viết. Docs của Mongoose có ghi EOL cho Mongoose 7 trong bản này, nên nếu đang ở 7.x hoặc 6.x thì đây là lúc lên lịch nâng major.
- **Phòng thủ nhiều lớp**: đừng chỉ dựa vào `sanitizeFilter`. Validate input bằng schema (zod, class-validator) để `req.query.name` chắc chắn là string trước khi chạm vào query.

## Góc học sâu

### Bulkhead và semaphore: giới hạn đồng thời để một tài nguyên không kéo sập cả service
`max_concurrency` của FastAPI là một semaphore: một bộ đếm N slot, ai lấy được slot mới chạy, ai không lấy được thì chờ, xong việc trả slot. Trong code FastAPI dùng `anyio.Semaphore`, mỗi object `Depends()` có một semaphore riêng cho từng event loop.

Vì sao cần ở tầng ứng dụng khi pool đã có giới hạn? Pool cũng chặn được, nhưng request đã chiếm worker thread, đã parse body, rồi mới đứng chờ connection và timeout. Chặn sớm ở tầng dependency giúp request chờ rẻ hơn, và tách bạch: endpoint báo cáo nặng có thể có semaphore riêng 2 slot, không ăn hết slot của endpoint đăng nhập. Đó là pattern **bulkhead**, giống vách ngăn tàu: một khoang ngập không làm chìm cả tàu.

Ba cái bẫy cần nhớ:

1. **Giới hạn là cục bộ**. Semaphore trong process chỉ biết process đó. N worker × M slot mới là con số chạm database. Muốn giới hạn toàn cụm phải dùng thứ dùng chung: PgBouncer, hoặc semaphore phân tán trên Redis.
2. **Deadlock khi giữ một slot và chờ slot khác**. Docs FastAPI nêu đúng ví dụ: `Depends(get_session, max_concurrency=1, use_cache=False)` dùng hai lần trong một request. Lần một giữ session đến cuối request, lần hai chờ session đó đóng, request đứng vĩnh viễn. Hai request giữ hai tài nguyên khác nhau theo thứ tự ngược nhau cũng kẹt như vậy.
3. **Quy tắc chống deadlock kinh điển**: luôn lấy tài nguyên theo cùng một thứ tự, và giảm thời gian giữ slot. Với dependency `yield`, cân nhắc `scope="function"` để trả slot ngay khi handler xong thay vì chờ gửi xong response.

Trong NestJS không có sẵn option tương tự, nhưng ý tưởng giống hệt: một semaphore (ví dụ thư viện `p-limit` hoặc tự viết) bọc quanh đoạn gọi tài nguyên đắt, cộng với pool size của TypeORM/Prisma đặt khớp.

## Tối ưu dùng AI

### Chủ đề hôm nay: quy trình khám phá, plan, làm, kiểm chứng với coding agent

Lỗi phổ biến nhất khi giao task cho agent là nhảy thẳng vào sửa code: agent đọc vài file, đoán kiến trúc, sửa, báo "done". Với task nhỏ thì không sao, với task chạm nhiều file thì bạn thành người sửa lại. Tách thành bốn pha giúp bạn chặn sai lầm ở pha rẻ nhất.

**Khi nào bỏ qua plan**: sửa typo, đổi tên biến, thêm một log, những việc bạn tả được diff trong một câu. Plan chỉ đáng khi task chạm nhiều file, bạn chưa rõ code hiện tại, hoặc có hai cách làm hợp lý mà bạn có ý thích riêng.

**Pha 1, khám phá (chưa cho sửa)**. Trong Claude Code, bật plan mode bằng `Shift+Tab`, prefix prompt bằng `/plan`, hoặc khởi động bằng `claude --permission-mode plan`. Ở plan mode agent đọc file, chạy lệnh để tìm hiểu, nhưng không sửa source cho đến khi bạn duyệt plan.

```text
/plan Tôi muốn thêm giới hạn số request đồng thời dùng DB session trong service FastAPI này.
Trước khi đề xuất gì, hãy tìm và báo lại:
1. Engine và pool được tạo ở đâu, pool_size, max_overflow đang là bao nhiêu
2. Các chỗ tạo Session không qua dependency get_session (background task, script, worker)
3. Số worker Uvicorn/Gunicorn trong Dockerfile hoặc compose
4. Test hiện có cho tầng DB và lệnh chạy test
Chưa sửa file nào.
```

**Pha 2, plan**. Yêu cầu plan có danh sách file sẽ sửa, thứ tự, và cách kiểm chứng. Nhấn `Ctrl+G` để mở plan trong editor và sửa trực tiếp trước khi duyệt. Đây là lúc rẻ nhất để nói "không, đừng thêm thư viện mới" hay "giữ nguyên API public".

```text
Viết plan gồm:
- Các file sẽ sửa và lý do cho từng file
- Quyết định thiết kế: giới hạn bao nhiêu, vì sao (dựa trên pool size và số worker vừa tìm)
- Rủi ro: chỗ nào một request có thể cần hai session cùng lúc
- Cách kiểm chứng: lệnh test, và một test mới chứng minh request thứ N+1 phải chờ
Không viết code trong plan. Khi tôi duyệt, lưu plan vào PLAN.md trước khi sửa code.
```

**Pha 3, làm**. Duyệt plan, agent thoát plan mode và bắt đầu sửa. Docs Claude Code khuyên xem phút đầu, nhấn `Esc` ngay khi agent đi lệch, và sau hai lần sửa hướng không được thì `/clear` rồi viết lại một prompt tốt hơn thay vì sửa lần thứ ba.

**Pha 4, kiểm chứng**. Theo docs, agent dừng khi việc "trông như xong"; nếu không có gì trả về pass hoặc fail thì bạn chính là test suite. Đưa cho nó một check chạy được và đòi bằng chứng:

```text
Chạy `pytest tests/db -q` và `ruff check .`, sửa đến khi cả hai pass.
Khi xong, dán lệnh đã chạy và output cuối cùng, không chỉ ghi "tests pass".
```

Rồi review bằng một context không dính lập luận của người viết code:

```text
use a subagent to review the diff against PLAN.md, check every item in the plan is implemented
and the listed risks have tests, report gaps that affect correctness and skip style
```

Docs nhắc giữ phần `skip style`: reviewer được bảo tìm lỗi thì luôn tìm ra "cái gì đó", sửa hết sẽ thành thêm abstraction và test cho trường hợp không thể xảy ra.

Checklist ngắn để dán vào ghi chú:

- Task chạm từ 3 file trở lên hoặc bạn chưa đọc code liên quan: dùng plan mode.
- Prompt khám phá liệt kê câu hỏi cụ thể và ghi rõ "chưa sửa file nào".
- Plan phải có mục "cách kiểm chứng" với lệnh cụ thể.
- Sửa plan bằng `Ctrl+G` trước khi duyệt, không duyệt rồi mới sửa hướng.
- Kết thúc bằng output của lệnh check, không chấp nhận "done" suông.

### Áp dụng ngay hôm nay
Chọn một task trong backlog chạm từ 3 file trở lên. Mở Claude Code bằng `claude --permission-mode plan`, dán prompt khám phá ở trên (thay câu hỏi cho hợp task), đọc plan và sửa ít nhất một điểm bằng `Ctrl+G` trước khi duyệt. Ghi lại plan có sót gì so với hiểu biết của bạn về codebase: đó là thứ nên thêm vào CLAUDE.md.
