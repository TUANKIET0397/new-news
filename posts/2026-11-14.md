# Tech Radar 14/11/2026: NestJS 12.5 hạ giới hạn WebSocket xuống 1 MB, FastAPI 0.162.6 bỏ Python 3.10

> Hôm nay đáng đọc nhất là NestJS 12.5.0: hàng loạt giới hạn mặc định mới cho WebSocket, TCP, gRPC, RabbitMQ, và TCP server không khai báo host giờ chỉ nghe trên localhost, dễ làm microservice "biến mất" sau khi nâng cấp. FastAPI có hai bản trong một ngày: 0.162.6 bỏ Python 3.10, 0.162.7 sửa cleanup của dependency `yield` khi request bị hủy. Ai chạy NestJS microservice hoặc FastAPI trên image Python cũ nên đọc trước khi bump.

## Điểm nóng hôm nay

### NestJS 12.5.0 và 11.2.10: giới hạn mặc định khắp transport, nhiều lỗi cấu hình chuyển thành lỗi lúc startup
Ngày 12/11 NestJS ra 12.5.0 và bản backport 11.2.10. Đây là bản tiếp nối hướng "siết giới hạn đầu vào" từ 12.2, nhưng lần này chạm vào gần như mọi transport:

- `WsAdapter` có `maxPayload`, mặc định 1 MB (trước là 100 MB). Message lớn hơn sẽ đóng kết nối với code 1009. `maxPayload` khai báo ở gateway được ưu tiên, `0` là bỏ giới hạn.
- `IoAdapter` có `maxWaitingMessages`, mặc định 10.000 message chờ cho mỗi event của một client.
- TCP server: `maxConcurrentMessages` mặc định 1000 mỗi connection; `maxBufferSize` giảm từ 128 Mi xuống 16 Mi ký tự và giờ tính theo từng packet.
- **TCP `host` để trống hoặc không set giờ nghe trên localhost.** Muốn nghe mọi interface phải ghi rõ `host: '0.0.0.0'` hoặc `'::'`.
- gRPC server có `maxPendingResponses` mặc định 1000; stream mà client không đọc response sẽ fail với `RESOURCE_EXHAUSTED`. RabbitMQ có `maxMessageSize` 16 MiB, Redis transport có `maxWildcardChannelLength` 1024.
- Multipart trên Express và Node adapter mặc định tối đa 1000 part; Fastify multipart có `limits.jsonFieldsSize` 1 MiB.
- Giới hạn set là `NaN` giờ quay về default thay vì tắt giới hạn. Set option upload là `undefined` hoặc `null` ở route thì giữ giá trị của module; muốn bỏ giới hạn dùng `Infinity`.
- `ClassSerializerInterceptor` áp `@Exclude()` và groups cho từng object trong response stream (mỗi dòng NDJSON). Trước đây các dòng stream có thể lọt field nhạy cảm.
- `SyntaxError` hoặc `URIError` không có status 400 trên Express/Node giờ là 500 có log, không còn là 400 kèm message.
- Guard, interceptor, pipe không chạy được (ví dụ abstract class làm token, class truyền vào `useValue` của `APP_GUARD`) và entry `forRoutes()`/`exclude()` sai giờ làm app dừng ngay lúc startup.

Vì sao đáng chú ý: thay đổi `host` của TCP là kiểu lỗi chỉ lộ ra khi deploy. Trong Docker Compose, service gọi sang microservice TCP qua tên container sẽ bị connection refused vì server chỉ nghe localhost trong container của nó. Release note cũng dặn nâng `@nestjs/core` và các package platform cùng lúc.

Áp dụng: trước khi bump, grep `Transport.TCP` và thêm `host: '0.0.0.0'` ở những chỗ chạy trong container; kiểm tra gateway WebSocket nào nhận payload lớn hơn 1 MB (upload ảnh base64 qua socket là ví dụ hay gặp) và set `maxPayload` tường minh. Dự án còn ở 11.x lên 11.2.10 để có các fix validation, SSE và lỗi startup tương tự.

Nguồn: [NestJS v12.5.0](https://github.com/nestjs/nest/releases/tag/v12.5.0), [NestJS releases](https://github.com/nestjs/nest/releases)

### FastAPI 0.162.6 bỏ Python 3.10, 0.162.7 sửa cleanup dependency `yield` khi request bị hủy
Hai bản cùng ngày 13/11. 0.162.6 có đúng một thay đổi: breaking change bỏ hỗ trợ Python 3.10 (PR #16737). 0.162.7 sửa việc dọn dẹp của async dependency dùng `yield` khi request bị cancel (PR #16739). Release note và PR không mô tả triệu chứng cụ thể, nên mình chỉ nói được phạm vi: code sau `yield` trong dependency async, đúng chỗ bạn thường đóng DB session hoặc trả connection về pool.

Release note cũng nhắc FastAPI có một skill chính thức giúp coding agent dùng tính năng và pattern đúng với phiên bản đang cài, cài bằng `uvx library-skills` trong project.

Vì sao đáng chú ý: nhiều Dockerfile vẫn dùng `python:3.10-slim`. Trên Python 3.10, pip bỏ qua các bản khai báo `Requires-Python` cao hơn và lặng lẽ cài bản cũ hơn, nên bạn sẽ không nhận được fix của 0.162.7 mà không hề có lỗi build. Áp dụng: kiểm tra base image, nâng lên Python 3.11+ trước khi lên 0.162.6. Nếu app có endpoint dài (stream, upload) và client hay hủy giữa chừng, nâng lên 0.162.7 và theo dõi số connection DB đang mở.

Nguồn: [FastAPI 0.162.6](https://github.com/fastapi/fastapi/releases/tag/0.162.6), [FastAPI 0.162.7](https://github.com/fastapi/fastapi/releases/tag/0.162.7), [PR #16739](https://github.com/fastapi/fastapi/pull/16739)

### alibaba/open-code-review: CLI review code bằng AI, pipeline cố định kết hợp agent
Repo đứng đầu GitHub Trending hôm nay. README mô tả `ocr` xuất phát từ trợ lý review nội bộ của Alibaba. Phần tất định (chọn file, gom file liên quan thành đơn vị review, match rule theo file, định vị comment theo dòng) do code làm; phần cần phán đoán và đi tìm context (đọc cả file, search codebase) giao cho agent có tool use. Output là comment chính xác tới từng dòng. Có `ocr scan` để review cả file thay vì diff, và delegation mode để coding agent đang dùng (qua skill hoặc lệnh `/open-code-review:delegate-review`) tự chạy review bằng model của nó, không cần API key riêng.

Vì sao đáng chú ý: thiết kế "deterministic trước, LLM sau" là pattern đúng cho mọi tính năng AI trong backend: phần nào viết được bằng code thì đừng để model đoán. Áp dụng: chạy `ocr review --from main --to <branch>` trước khi mở PR; README cho biết có tích hợp GitHub Actions và GitLab CI. Repo hỗ trợ provider tương thích OpenAI và Anthropic, license Apache-2.0, cần Git 2.41 trở lên.

Nguồn: [alibaba/open-code-review](https://github.com/alibaba/open-code-review), [GitHub Trending](https://github.com/trending)

### tailscale/tailcat: netcat chạy trên data plane của Tailscale, không cần tài khoản
Tailcat là CLI và thư viện Go, open source từ tháng 8/2026. Server chạy `tailcat` để nhận một địa chỉ ngắn; client dùng địa chỉ đó để kết nối. Traffic mã hóa đầu cuối bằng WireGuard, kết nối khởi động qua DERP relay rồi thử NAT traversal để chuyển sang UDP peer-to-peer. Tunnel chạy hoàn toàn ở userspace nên không cần root, không đổi routing hay DNS. License BSD-3-Clause.

Vì sao đáng chú ý: với dev làm VPS, đây là cách nhanh để mở tạm một port ra máy khác mà không phải mở firewall hay dựng VPN. Ví dụ trong README: `tailcat forward tcXXXX 18080:8080 3306` chuyển port 8080 và MySQL 3306 của máy kia về máy bạn. Lưu ý README nói DERP relay công cộng có rate limit, và việc đưa cổng database ra ngoài, dù qua tunnel mã hóa, vẫn nên chỉ làm tạm thời rồi tắt.

## Góc học sâu

### Bounded buffer và backpressure: vì sao mọi hàng đợi phải có giới hạn
Phần lớn thay đổi trong NestJS 12.5 là cùng một ý: mỗi chỗ giữ dữ liệu trong bộ nhớ (buffer TCP, message đang chờ của Socket.IO, response gRPC chưa gửi được) đều phải có trần.

Bản chất: khi producer nhanh hơn consumer, dữ liệu dồn vào hàng đợi ở giữa. Nếu hàng đợi không giới hạn, độ trễ tăng dần rồi process hết RAM và bị OOM kill, kéo theo mọi client khác trên cùng instance. Một client chậm hoặc cố ý không đọc (slowloris ở tầng ứng dụng) là đủ. Có ba cách xử lý khi hàng đợi đầy:

1. **Backpressure**: báo producer chậm lại. Trong Node.js, `writable.write()` trả `false` khi buffer vượt `highWaterMark`; code đúng phải chờ event `drain` trước khi ghi tiếp. TCP tự làm việc này bằng flow control khi app ngừng đọc socket.
2. **Từ chối**: trả lỗi ngay, như gRPC `RESOURCE_EXHAUSTED` hay HTTP 429/503. Client biết để retry có backoff.
3. **Bỏ bớt**: drop message cũ hoặc mới, chấp nhận được với dữ liệu kiểu telemetry, không được với đơn hàng.

Đóng kết nối khi vượt `maxPayload` (code 1009) là dạng từ chối. Áp dụng cho code của bạn: mỗi khi viết `const queue = []` để gom job, mảng cache tạm, hay `Promise.all` trên một danh sách do user gửi lên, hãy hỏi "nó lớn tối đa bao nhiêu và chuyện gì xảy ra khi vượt". Với BullMQ hay RabbitMQ, giới hạn concurrency của worker (`prefetch` trong RabbitMQ) chính là backpressure: broker giữ message thay vì đẩy hết vào RAM của worker.

## Tối ưu dùng AI

### Chủ đề hôm nay: eval nhỏ cho prompt, đo trước khi sửa

Khi một tính năng AI trong backend trả kết quả sai (phân loại ticket, trích xuất field từ email, gợi ý tag), phản xạ thường là sửa prompt rồi thử tay vài câu. Cách đó không cho biết lần sửa có làm hỏng các case khác không. Tài liệu Claude về develop tests đưa ra ba nguyên tắc:

- **Bám đúng task**: bộ test phản ánh phân bố input thật, cộng thêm edge case như input rỗng, input quá dài, input không liên quan, case mà chính người cũng phân vân.
- **Tự động hóa khi có thể**: thiết kế câu hỏi để chấm được bằng code (exact match, string match, so JSON), chỉ dùng LLM chấm khi cần phán đoán.
- **Ưu tiên số lượng**: docs viết rõ nhiều câu hỏi chấm tự động với tín hiệu hơi kém vẫn tốt hơn ít câu chấm tay chất lượng cao.

Về cách chấm, docs xếp theo thứ tự: chấm bằng code (nhanh, tin cậy, nhưng thiếu sắc thái), LLM chấm (nhanh, linh hoạt, nhưng phải kiểm tra độ tin cậy trước khi scale), người chấm (chất lượng cao nhưng chậm, tránh nếu được). Khi dùng LLM chấm: bắt nó trả kết quả có cấu trúc kiểu `correct`/`incorrect` hoặc thang 1 đến 5, bật thinking để grader suy luận trước khi cho điểm, và nên dùng model khác với model sinh output.

Quy trình từng bước:

1. Lấy 30 đến 50 input thật từ log (đã xóa dữ liệu cá nhân), ghi đáp án đúng vào một file JSONL.
2. Viết script chạy prompt hiện tại trên cả bộ, chấm bằng code, in tỷ lệ đúng và danh sách case sai. Đây là baseline.
3. Sửa prompt, chạy lại, chỉ giữ thay đổi nếu điểm tăng và không có case nào từng đúng giờ sai.
4. Mỗi bug thực tế từ production thành một dòng mới trong file test.

Template tối thiểu bằng Python với Anthropic SDK, bài toán phân loại ticket hỗ trợ:

```python
# eval_ticket.py: chạy bằng `python eval_ticket.py`
import json
import anthropic

client = anthropic.Anthropic()  # đọc ANTHROPIC_API_KEY từ env
PROMPT = open("prompts/classify_ticket.txt").read()  # có placeholder {ticket}
LABELS = {"billing", "bug", "account", "other"}

def classify(ticket: str) -> str:
    msg = client.messages.create(
        model="claude-haiku-5-5",
        max_tokens=20,
        messages=[{"role": "user", "content": PROMPT.format(ticket=ticket)}],
    )
    return msg.content[0].text.strip().lower()

cases = [json.loads(line) for line in open("evals/tickets.jsonl")]
fails = []
for c in cases:
    got = classify(c["input"])
    if got not in LABELS or got != c["expected"]:
        fails.append((c["input"][:60], c["expected"], got))

print(f"pass {len(cases) - len(fails)}/{len(cases)}")
for f in fails:
    print("FAIL", f)
```

File `evals/tickets.jsonl` mỗi dòng một case:

```text
{"input": "Tôi bị trừ tiền 2 lần cho đơn #1234", "expected": "billing"}
{"input": "Bấm nút Xuất PDF thì trang trắng", "expected": "bug"}
{"input": "", "expected": "other"}
```

Commit cả prompt và file test vào repo, cạnh code gọi API. Khi nhờ coding agent sửa prompt, đưa luôn lệnh `python eval_ticket.py` làm điều kiện xong: agent phải dán output pass/fail trước và sau khi sửa.

Nguồn: [Claude Docs: Define success criteria and build evaluations](https://platform.claude.com/docs/en/test-and-evaluate/develop-tests)

### Áp dụng ngay hôm nay
Chọn một prompt đang chạy trong dự án của bạn (hoặc một prompt bạn hay dán vào ChatGPT/Claude để làm việc lặp lại). Lấy 10 input thật, ghi đáp án mong muốn vào một file JSONL, chạy prompt hiện tại trên cả 10 và đếm số câu đúng. Con số đó là baseline của bạn; lần sau sửa prompt, chạy lại và so.
