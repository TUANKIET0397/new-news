# Tech Radar 20/11/2026: PostgreSQL 19 chính thức ra mắt với `REPACK (CONCURRENTLY)` và `WAIT FOR LSN`, FastAPI 0.164 thêm giới hạn kích thước body

> PostgreSQL 19 GA ngày 19/11: dọn bloat bằng `REPACK (CONCURRENTLY)` mà không khóa bảng, đọc từ replica vẫn thấy dữ liệu vừa ghi nhờ lệnh `WAIT FOR LSN`, nhưng cũng có vài thay đổi mặc định cần đọc trước khi nâng (JIT tắt, `max_locks_per_transaction` đổi cách tính). Dân FastAPI có `max_body_size` và `form_limits` ngay trong framework, khỏi phải tự viết middleware chặn upload quá cỡ. Ai chạy PostgreSQL production hoặc API nhận upload nên đọc kỹ hai mục đầu.

## Điểm nóng hôm nay

### PostgreSQL 19.0: `REPACK`, `WAIT FOR LSN`, `pg_plan_advice` và logical replication bật không cần restart
Release notes chính thức ghi ngày phát hành 2026-11-19, tag `REL_19_0` đã có trên repo từ 16/11. Các điểm nổi bật theo phần Overview:

- Lệnh mới `REPACK` viết lại toàn bộ bảng sang file mới để trả dung lượng của dead tuple về cho hệ điều hành. `REPACK (CONCURRENTLY)` làm việc đó mà không chặn đọc ghi trên bảng. Có `USING INDEX` để sắp xếp lại vật lý theo index, tức là làm việc của `CLUSTER`.
- Lệnh mới `WAIT FOR LSN` cho phép đạt read-your-writes trên standby: ghi ở primary, lấy LSN, rồi trên replica chờ tới LSN đó trước khi đọc.
- Extension `pg_plan_advice` để điều khiển quyết định của planner, và `pg_stash_advice` tự áp plan advice theo query.
- Logical replication bật được mà không cần restart server khi `wal_level` đang là `replica`. Có biến mới `effective_wal_level` để xem mức WAL thực tế.
- Logical replication cho cả giá trị của sequence.
- Autovacuum chạy song song trên index của bảng, và có cơ chế chấm điểm để ưu tiên bảng nào vacuum trước.
- Hiệu năng: tự scale số I/O worker, kiểm tra foreign key nhanh hơn, thêm tối ưu planning và execution.

Vì sao đáng chú ý: `REPACK (CONCURRENTLY)` đưa vào core thứ mà trước giờ phải dùng extension ngoài như pg_repack. Bảng `orders`, `events`, `jobs` bị update/delete liên tục thường phình to dù `VACUUM` vẫn chạy, vì `VACUUM` chỉ đánh dấu chỗ trống để tái dùng chứ không trả đĩa. Còn `WAIT FOR LSN` giải quyết lỗi kinh điển khi tách đọc ghi: user vừa sửa profile, request kế tiếp đọc từ replica chưa kịp replay và thấy dữ liệu cũ.

Áp dụng: backend NestJS/Laravel/FastAPI dùng một primary và một hay nhiều read replica, bảng log hoặc queue tự viết trên PostgreSQL bị bloat, team đang cân nhắc Debezium hoặc CDC qua logical replication. Chi tiết cách dùng `WAIT FOR LSN` ở phần Góc học sâu.

Nguồn: [Release 19 (doc/src/sgml/release-19.sgml tại REL_19_0)](https://github.com/postgres/postgres/blob/REL_19_0/doc/src/sgml/release-19.sgml), [REPACK reference](https://github.com/postgres/postgres/blob/REL_19_0/doc/src/sgml/ref/repack.sgml), [WAIT reference](https://github.com/postgres/postgres/blob/REL_19_0/doc/src/sgml/ref/wait.sgml)

### PostgreSQL 19: những thay đổi tương thích nên đọc trước khi nâng
Phần "Migration to Version 19" dài, đây là các mục dễ đụng tới nhất với app web thông thường:

| Thay đổi | Ảnh hưởng thực tế |
|---|---|
| JIT tắt mặc định | Ai chạy nhiều query phân tích lớn phải tự bật lại `jit`. OLTP thường được lợi vì JIT costing bị đánh giá là không đáng tin. |
| `max_locks_per_transaction` mặc định 64 lên 128 | Cách cấp phát lock đổi, nên nếu bạn đã chỉnh tay thì phải nhân đôi giá trị để giữ cùng sức chứa. |
| `standard_conforming_strings` luôn bật | Dump tạo bằng `pg_dump` cũ với setting này đang `off` sẽ không load đúng vào 19. Hãy dump bằng `pg_dump` bản 19. |
| Cảnh báo sau khi đăng nhập bằng MD5 password | Log sẽ có warning. Nên chuyển sang SCRAM, hoặc tắt bằng `md5_password_warnings`. |
| Bỏ RADIUS, bỏ `io_workers` | `io_workers` được thay bằng bốn biến mới cho cơ chế tự scale I/O worker. |
| `json_array()` không có dòng nào trả mảng rỗng | Trước đây trả `NULL`. Code nào kiểm tra `IS NULL` cần xem lại. |
| Opclass mặc định cho `inet`/`cidr` chuyển từ btree_gist sang GiST | `pg_upgrade` sẽ từ chối cluster có index btree_gist trên `inet`/`cidr`, vì opclass cũ có thể bỏ sót dòng. |
| Parallel vacuum chia chung `vacuum_cost_limit` | `VACUUM` song song có cost delay có thể chạy chậm hơn trước. |
| Full text search và pg_trgm dùng locale provider của database | DB dùng ICU hoặc builtin provider nên reindex index full text, pg_trgm sau khi `pg_upgrade`. |

Áp dụng: đừng nâng production ngay tuần đầu. Dựng một bản 19 trong Docker, restore dump bằng `pg_dump` của 19, chạy test suite của app và so `EXPLAIN ANALYZE` của vài query nặng nhất.

### FastAPI 0.164.0 và 0.165.0: `max_body_size` và `form_limits` trong framework
Ngày 18/11 FastAPI ra liền hai bản. 0.164.0 thêm giới hạn kích thước request body (#16781), 0.165.0 thêm giới hạn khi parse form (#16784). Theo trang docs mới "Request Body Limits":

- `max_body_size` tính bằng byte, đặt được trên `FastAPI(...)`, `APIRouter(...)`, `include_router()` và từng path operation. Để `None` (mặc định) thì kế thừa từ router hoặc app bao ngoài, không đặt ở đâu thì body không giới hạn.
- FastAPI đếm số byte thực sự đọc được, kể cả khi client gửi chunked không có `Content-Length`. Vượt giới hạn thì dừng đọc và trả 413 Content Too Large nếu response chưa bắt đầu.
- Giới hạn tính cho toàn bộ body: nhiều file trong cùng request, các form field và phần encoding multipart cộng chung một hạn mức.
- `form_limits` có `max_fields` (mặc định 1.000), `max_files` (mặc định 1.000), `max_part_size` (mặc định 1 MiB cho mỗi text field). Vượt các giới hạn parser này trả HTTP 400.
- Lưu ý middleware: nếu middleware gọi `await request.body()` trước khi FastAPI chọn route, giới hạn của app được áp. App giới hạn 1 MiB sẽ chặn upload 2 MiB trước khi nó tới router cho phép 100 MiB.

Vì sao đáng chú ý: trước đây chặn upload quá cỡ phải dựa vào `client_max_body_size` của Nginx hoặc tự viết middleware đếm byte, và hay quên mất trường hợp chunked không có `Content-Length`. Giới hạn đặt theo từng route trong code thì review được, test được.

Áp dụng: API nhận JSON nhỏ nhưng có vài endpoint upload ảnh hay CSV. Đặt mức thấp ở app, mở rộng riêng cho router upload. FastAPI 0.165.0 yêu cầu Python 3.11+ và Starlette 1.6.0+.

Nguồn: [FastAPI releases](https://github.com/fastapi/fastapi/releases), [docs: Request Body Limits](https://github.com/fastapi/fastapi/blob/0.165.0/docs/en/docs/advanced/request-body-limits.md)

### Next.js 16.5.0-canary.56: Switchyard, proxy Go thử nghiệm đứng trước `next start`
PR #101695 (merge 19/11, sau đó đổi tên thành Switchyard ở #102035) thêm một proxy viết bằng Go, chạy trước `next start`. Bật bằng biến môi trường `__NEXT_EXPERIMENTAL_SWITCHYARD=1`. Switchyard nghe ở port public, Node chạy ở port loopback riêng. Hiện nó chỉ forward nguyên request sang Node, chưa ra quyết định routing nào. Package `next` không kèm binary Go, bạn phải trỏ `__NEXT_EXPERIMENTAL_SWITCHYARD_BINARY` tới binary hoặc build `next` với `NEXT_BUILD_SWITCHYARD=1` (cần Go 1.24+). Chỉ hỗ trợ Linux và macOS, không áp dụng cho `next dev`, `server.js` standalone hay custom server.

Vì sao đáng chú ý: đây là tín hiệu Next.js định chuyển một phần việc của server (routing, có thể là cache) ra khỏi Node. Theo benchmark của tác giả trên một máy, độ trễ tăng khoảng 50 µs mỗi request, route đơn giản giảm khoảng 12,6% throughput ở concurrency 64, trang dynamic và streaming gần như không đổi. PR liệt kê các khác biệt: reason phrase tùy chỉnh bị mất, tên header response bị chuẩn hóa chữ hoa thường, WebSocket không được chờ khi shutdown.

Áp dụng: chưa nên dùng cho production. Nếu bạn tự host Next.js trên VPS sau Nginx, theo dõi hướng đi này để biết sau này có thể bỏ bớt lớp proxy nào. Danh sách khác biệt cũng là checklist tốt khi đặt bất kỳ reverse proxy nào trước app Node.

Nguồn: [v16.5.0-canary.56](https://github.com/vercel/next.js/releases/tag/v16.5.0-canary.56), [PR #101695](https://github.com/vercel/next.js/pull/101695)

## Cài đặt và dùng thử

### PostgreSQL 19 trong Docker
Repo `docker-library/postgres` đã cập nhật version 19 lên `19.0`, nhưng tại thời điểm viết, Docker Hub mới có tag `19rc2`. Khi tag `19` xuất hiện thì dùng nó, còn trước đó có thể thử các lệnh dưới đây trên `19rc2`. Lệnh chạy theo mẫu trong README của image chính thức:

```bash
docker run --name pg19 -e POSTGRES_PASSWORD=mysecretpassword -d postgres:19
docker exec -it pg19 psql -U postgres
```

Thử `REPACK` (cú pháp từ trang reference):

```sql
-- dọn bloat, không chặn đọc ghi
REPACK (CONCURRENTLY, VERBOSE) orders;

-- sắp xếp lại vật lý theo index, kèm ANALYZE
REPACK (ANALYZE) orders USING INDEX orders_created_at_idx;

-- theo dõi tiến độ
SELECT * FROM pg_stat_progress_repack;
```

Lưu ý từ docs: cần quyền `MAINTAIN` trên bảng; `REPACK` từ chối bảng có index invalid; không dùng `REPACK` để chống transaction ID wraparound, việc đó vẫn là của `VACUUM`. `REPACK` không kèm tên bảng sẽ xử lý mọi bảng bạn có quyền, và dạng này không đi cùng `CONCURRENTLY`.

### FastAPI: giới hạn body theo app, router và route (cần FastAPI 0.164+ cho `max_body_size`, 0.165+ cho `form_limits`, Python 3.11+)

```bash
pip install --upgrade "fastapi[standard]"
```

Ví dụ từ docs chính thức:

```python
from fastapi import APIRouter, FastAPI, UploadFile

app = FastAPI(max_body_size=1 * 1024 * 1024)
uploads = APIRouter(prefix="/uploads", max_body_size=100 * 1024 * 1024)


@app.post("/items")
def create_item(item: dict):
    return item


@uploads.post("/")
def upload(file: UploadFile):
    return {"filename": file.filename, "size": file.size}


@uploads.post("/small", max_body_size=10 * 1024 * 1024)
def small_upload(file: UploadFile):
    return {"filename": file.filename, "size": file.size}


app.include_router(uploads)
```

`POST /items` dùng giới hạn 1 MiB của app, `POST /uploads/` dùng 100 MiB của router, `POST /uploads/small` có giới hạn riêng 10 MiB. Giới hạn form:

```python
from typing import Annotated

from fastapi import FastAPI, Form

app = FastAPI(form_limits={"max_fields": 5})


@app.post("/documents", form_limits={"max_part_size": 2 * 1024 * 1024})
async def create_document(text: Annotated[str, Form()]):
    return {"size": len(text)}
```

## Góc học sâu

### Read-your-writes khi tách đọc ghi sang replica: vì sao cần LSN
Replication trong PostgreSQL mặc định là bất đồng bộ. Primary ghi mọi thay đổi vào WAL (write-ahead log), mỗi vị trí trong WAL là một LSN (log sequence number). Standby nhận WAL rồi replay, nên luôn chậm hơn primary một khoảng, thường vài mili giây, lúc tải cao có thể vài giây. Nếu app ghi vào primary rồi đọc ngay từ replica, user có thể không thấy thứ họ vừa lưu. Đó là vi phạm read-your-writes, một mức consistency yếu hơn strong consistency nhưng là thứ người dùng mong đợi tối thiểu.

Các cách xử lý quen thuộc trước đây đều có giá:

- Đọc từ primary trong N giây sau khi ghi (sticky). Laravel có option `sticky` cho kết nối read/write làm đúng việc này trong cùng request. Đơn giản nhưng N là con số đoán.
- Synchronous replication với `synchronous_commit = remote_apply`. Đúng tuyệt đối nhưng mọi commit phải chờ standby, latency ghi tăng và standby chết thì primary bị treo commit.
- Đọc hết từ primary. Mất luôn lý do có replica.

`WAIT FOR LSN` cho cách thứ tư, chính xác hơn mà không làm chậm phần ghi:

1. Sau khi commit trên primary, lấy LSN (ví dụ trong docs dùng `SELECT pg_current_wal_insert_lsn();`).
2. Lưu LSN đó ở phía client: session, cookie, header, hoặc connection pooler.
3. Request đọc tiếp theo, trên replica chạy `WAIT FOR LSN '<lsn>' WITH (TIMEOUT '100ms', NO_THROW);` rồi mới query.
4. Nếu kết quả là `success` thì đọc trên replica. Nếu là `timeout` (replica đang lag) thì chuyển sang đọc ở primary. Nếu `not in recovery` thì server đã được promote, cần đánh giá lại.

Vài ràng buộc từ docs cần nhớ khi đưa vào code: `WAIT` phải là lệnh top-level, không chạy trong function hay `DO` block; đặt nó ngoài transaction hoặc là lệnh đầu tiên của transaction, trước bất cứ lệnh nào lấy lock hay snapshot, nếu không sẽ bị từ chối. Mặc định không có timeout nghĩa là chờ vô hạn, nên trong web request luôn đặt `TIMEOUT`. `NO_THROW` trả status thay vì raise error, giúp transaction không bị hỏng và code fallback gọn hơn.

Đây là pattern chung của mọi hệ thống có replica: đánh dấu "phiên bản" của lần ghi (LSN, offset Kafka, version của document) và để bên đọc chờ tới phiên bản đó. Hiểu nó rồi thì bạn nhận ra cùng ý tưởng ở MongoDB causal consistency, ở read-after-write của cache có version, hay ở cách tránh đọc stale sau khi publish event.

## Tối ưu dùng AI

### Chủ đề hôm nay: MCP server cho cả team, cấu hình một lần trong `.mcp.json`
Skill dạy agent *cách* làm việc theo quy trình của team. MCP server cho agent *quyền truy cập* vào hệ thống của team: database dev, issue tracker, tài liệu nội bộ, error tracking. Nếu mỗi người tự `claude mcp add` trên máy mình, cấu hình sẽ lệch nhau và người mới vào không biết agent có thể dùng gì. Claude Code giải quyết bằng scope:

| Scope | Nạp ở đâu | Chia sẻ với team | Lưu ở |
|---|---|---|---|
| Local (mặc định) | Chỉ project hiện tại | Không | `~/.claude.json` |
| Project | Chỉ project hiện tại | Có, qua git | `.mcp.json` ở root project |
| User | Mọi project của bạn | Không | `~/.claude.json` |

Quy trình đưa một MCP server thành công cụ chung của team:

1. Chọn đúng scope. Server mà ai trong repo cũng cần (tài liệu API nội bộ, database dev) để ở project scope. Server cá nhân (tài khoản riêng) để local hoặc user.
2. Thêm bằng lệnh, để file được ghi đúng định dạng:

```bash
claude mcp add --transport http shared-server --scope project https://example.com/mcp
```

3. Không commit secret. `.mcp.json` hỗ trợ `${VAR}` và `${VAR:-default}` trong `command`, `args`, `env`, `url`, `headers`. Mỗi người tự đặt biến môi trường:

```json
{
  "mcpServers": {
    "api-server": {
      "type": "http",
      "url": "${API_BASE_URL:-https://api.example.com}/mcp",
      "headers": {
        "Authorization": "Bearer ${API_KEY}"
      }
    }
  }
}
```

4. Cấp quyền tối thiểu cho tài khoản mà server dùng: user database chỉ đọc, chỉ trỏ vào môi trường dev hoặc staging, token issue tracker không có quyền xóa.
5. Ghi một đoạn ngắn trong CLAUDE.md hoặc AGENTS.md: server nào dùng cho việc gì, biến môi trường nào cần đặt, việc gì không được làm qua server đó.
6. Nắm cơ chế duyệt. Trong phiên tương tác, Claude Code hỏi trước khi dùng server project-scoped từ `.mcp.json` (đặt lại lựa chọn bằng `claude mcp reset-project-choices`). Nhưng với `claude -p`, Agent SDK và cloud session ngoài project, không có prompt nào để hỏi, server được nạp luôn. Chạy agent trong CI thì chủ động loại server không cần bằng `disabledMcpjsonServers` hoặc khởi động với `--strict-mcp-config`.

Checklist review một PR thêm MCP server vào `.mcp.json`:

- Server lấy từ nguồn chính thức của vendor, có phiên bản cố định không?
- Có secret nào viết thẳng trong file thay vì `${VAR}` không?
- Tài khoản server dùng có quyền ghi hay xóa trên production không?
- Output của tool có thể chứa nội dung do người ngoài viết (ticket, comment, email) không? Nếu có, đó là đường prompt injection, cần nghĩ tới hook chặn hành động nhạy cảm.
- CI có đang vô tình nạp server này không?

### Áp dụng ngay hôm nay
Mở `~/.claude.json` hoặc chạy `claude mcp list` trong repo bạn làm hằng ngày, tìm một MCP server mà đồng nghiệp cũng cần. Chuyển nó sang project scope bằng `claude mcp add ... --scope project`, thay mọi token bằng `${VAR}`, rồi thêm hai dòng vào CLAUDE.md nói server dùng cho việc gì và cần đặt biến nào. Mở PR và nhờ một người khác clone về thử.
