## Điểm nóng hôm nay

### Node.js báo trước security release ngày 11/11/2026
Ngày 3/11, Node.js đăng thông báo "Wednesday, November 11, 2026 Security Releases". Nội dung: sẽ có bản phát hành mới cho các dòng 26.x, 24.x và 22.x, trong mỗi dòng mức nghiêm trọng cao nhất được vá là High. Trang thông báo chưa có CVE ID hay mô tả lỗi cụ thể, và ghi rõ ngày 11/11 là "hoặc ngay sau đó". Các phiên bản End-of-Life cũng bị ảnh hưởng nhưng sẽ không có bản vá.

Vì sao đáng chú ý: đợt trước (21/10) đã vá ba lỗi High liên quan TLS/DNS, đợt này lại High nữa. Áp dụng: nếu service NestJS hoặc Next.js của bạn chạy trên Node 20 thì không còn đường vá chính thức, hãy lên kế hoạch lên 22, 24 hoặc 26 trước ngày này. Với image Docker, pin tag theo minor và có sẵn pipeline build lại để rebuild trong ngày có bản vá.

### GitHub spec-kit: toolkit cho spec-driven development
`github/spec-kit` (Python) đang trending với khoảng 810 sao trong ngày. Theo README, đây là toolkit mã nguồn mở của GitHub giúp coding agent đi theo quy trình có cấu trúc, dùng template và tài liệu kết quả có thể tái sử dụng. Quy trình chính là Spec-Driven Development (SDD): viết constitution (nguyên tắc), spec, plan, danh sách task rồi mới implement. README còn có quy trình sửa bug và đánh giá ý tưởng dưới dạng extension.

Áp dụng: hợp với feature backend có nhiều ràng buộc (auth, billing, migration) mà prompt một dòng thường làm lệch ý. Chi tiết cài đặt ở phần bên dưới.

Nguồn: [github/spec-kit](https://github.com/github/spec-kit)

## Cài đặt và dùng thử

### spec-kit
Yêu cầu theo README: Python 3.11+, `uv`, một AI coding agent được hỗ trợ; chạy trên Linux, macOS, Windows.

```bash
uv tool install specify-cli
specify init my-project --integration copilot
cd my-project
```

Sau đó mở coding agent trong thư mục dự án và chạy các lệnh sau trong khung chat của agent (không phải terminal). README ví dụ theo cú pháp lệnh của GitHub Copilot, agent khác có thể gọi khác đi:

```text
/speckit-constitution Create principles focused on code quality, testing, and maintainability.
/speckit-specify Build a photo organizer with albums grouped by date and a tile preview of each album.
/speckit-plan Use Vite with vanilla JavaScript. Keep images local and store metadata in SQLite.
/speckit-tasks
/speckit-implement
/speckit-converge
```

README khuyên xem lại kết quả từng bước, và lặp `implement` rồi `converge` cho đến khi `converge` báo `Converged`.

## Góc học sâu

### Graceful shutdown: để nâng cấp runtime không làm rơi request
Khi bản vá Node ra, thao tác thực tế là build lại image rồi thay container đang chạy. Nếu không xử lý tốt, mỗi lần thay là một đợt lỗi 502 ngắn. Bản chất vấn đề: orchestrator (Docker, systemd, Kubernetes) gửi `SIGTERM` rồi chờ một khoảng, hết khoảng đó gửi `SIGKILL`. Process cần làm đúng ba việc trong khoảng này:

1. Ngừng nhận kết nối mới (đóng listener) và báo load balancer rằng instance không còn healthy.
2. Chờ các request đang xử lý xong, có timeout rõ ràng nhỏ hơn thời gian chờ trước `SIGKILL`.
3. Đóng tài nguyên theo thứ tự ngược lại lúc mở: HTTP server, worker/queue consumer, rồi connection pool DB và Redis.

Điểm hay sai: queue consumer vẫn nhận job trong lúc đang tắt, dẫn tới job chạy dở và phải xử lý lại. Vì vậy job nên idempotent, và consumer cần ngừng pull job trước khi pool DB bị đóng. Nếu dùng NestJS, hook `enableShutdownHooks()` cùng các lifecycle hook như `onApplicationShutdown` là chỗ gắn logic này; kiểm tra trong docs của framework cho phiên bản bạn đang dùng. Rolling update kiểu "bật instance mới, đợi healthy, rồi mới tắt instance cũ" là cách giảm rủi ro nhất khi vá gấp.

## Tối ưu dùng AI

### Chủ đề hôm nay: viết spec ngắn trước khi giao việc cho agent

Tài liệu Best practices của Claude Code nói thẳng: khi bạn chưa biết chính xác mình muốn gì, đừng cố nghĩ hết rồi mới prompt, hãy bảo Claude phỏng vấn bạn. Claude sẽ hỏi dạng trắc nghiệm về những phần bạn chưa chốt (ví dụ giới hạn theo user hay theo API key, request vượt giới hạn thì xử lý ra sao, cái gì nằm ngoài phạm vi), hỏi tới khi đủ để viết thành spec. Sau khi có `SPEC.md`, tài liệu khuyên mở session mới để bắt đầu build với context sạch và một định nghĩa "xong" bằng văn bản, rồi dùng chính file đó làm chuẩn để review.

Quy trình 4 bước:

1. Phỏng vấn để ra spec. Prompt mẫu (lấy từ tài liệu):

```text
I want to add rate limiting to the public API but haven't thought it through yet.
Interview me until you could write the spec, then write it to SPEC.md.
```

2. Tự đọc `SPEC.md`, xóa câu nào bạn không đồng ý. Spec nên có ba phần: yêu cầu, edge case cần có test, và những thứ không làm.
3. Mở session mới, giao việc bằng spec:

```text
Implement the rate limiter described in SPEC.md. Run the existing tests and typecheck
before saying it is done. If a requirement is ambiguous, ask me instead of guessing.
```

4. Review theo spec bằng subagent, theo mẫu trong tài liệu:

```text
use a subagent to review the rate limiter diff against SPEC.md, check every requirement
is implemented and the listed edge cases have tests, report gaps that affect correctness and skip style
```

Template spec tối thiểu cho feature backend:

```markdown
# Spec: <tên feature>
## Mục tiêu
Một hai câu, nêu hành vi quan sát được.
## Yêu cầu
- ...
## Edge case cần có test
- ...
## Ngoài phạm vi
- ...
## Cách kiểm chứng
Lệnh chạy test/lint/typecheck và kết quả mong đợi.
```

Cùng ý tưởng đó, `spec-kit` ở trên đóng gói thành bộ lệnh `constitution`, `specify`, `plan`, `tasks`, còn `/grill-me` của mattpocock/skills là phiên bản skill của bước phỏng vấn. Với việc nhỏ như sửa một dòng, đừng viết spec: tài liệu cũng nói prompt mơ hồ cho việc khám phá là hoàn toàn ổn.

Nguồn: [Best practices for Claude Code](https://code.claude.com/docs/en/best-practices)

### Áp dụng ngay hôm nay
Chọn một ticket nhỏ sắp làm (ví dụ thêm rate limit hoặc validation cho một endpoint). Dành 15 phút: chạy prompt phỏng vấn ở bước 1, trả lời các câu hỏi, đọc lại `SPEC.md` và chốt mục "Ngoài phạm vi". Chưa cần implement; chỉ cần có spec để mai giao cho agent trong session mới.
